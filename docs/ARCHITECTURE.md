### Web 面板认证文件结构（安全分离）

当前版本将认证数据拆分为**两个独立文件**，实现密码与 JWT 密钥的物理隔离：

| 文件 | 存储内容 | Web 端可读 | 说明 |
|------|---------|:----------:|------|
| `web_data/auth.json` | 密码哈希、salt、hash_version、password_changed 标志 | ❌ 不可读 | 密码相关数据 |
| `web_data/jwt_secret.json` | JWT 签名密钥、临时密码明文副本、重载标记 | ❌ 不可读 | JWT 与会话管理数据 |

> **为什么分离？** 如果攻击者获取了包含密码哈希的文件，不应同时获得 JWT 签名密钥——否则可以绕过密码验证直接伪造登录令牌。两个文件的独立存储使单一泄露的影响范围最小化。

#### 自动迁移机制

如果你是从旧版升级，且旧版的 `auth.json` 中同时包含密码和 JWT secret，系统会在启动时自动执行以下迁移：

1. 检测到 `auth.json` 中存在 `jwt_secret` 字段 → 将其提取并写入新建的 `jwt_secret.json`
2. 从 `auth.json` 中删除 `jwt_secret` 和 `_web_initiated_reload` 字段
3. 迁移完成后 `auth.json` 仅保留密码数据，`jwt_secret.json` 管理 JWT 相关数据
4. 整个过程无需用户手动操作，日志中会输出迁移确认信息

#### 旧版根目录 auth.json 兼容

如果你是从更早的版本升级，并且旧版本的密码文件保存在插件数据**根目录**下的 `auth.json`（而非 `web_data/` 子目录），请在升级前先将该文件移动到 `web_data/auth.json`。否则新版本会在 `web_data/` 下重新生成默认密码。

如果你发现当前插件数据目录中同时存在：
- 根目录 `auth.json`
- `web_data/auth.json`

那么根目录那个通常是旧版本遗留文件；在确认当前 Web 面板已经正常使用 `web_data/auth.json` 登录后，可以手动删除根目录旧文件。

### Web 面板密码哈希升级说明

当前版本起，Web 面板密码默认使用 `Argon2id` 内存硬化哈希，替代旧版 `PBKDF2-SHA256`，显著提升抗 GPU 暴力破解能力。

- 新生成密码、用户主动修改后的密码、以及重置后生成的默认随机密码，都会直接保存为 `Argon2id`
- 若现有 `web_data/auth.json` 仍为旧版 `PBKDF2-SHA256` 哈希，用户使用原密码首次登录成功后会自动透明迁移到 `Argon2id`
- 迁移过程无需用户手动改密，也不会影响原密码本身

`web_data/auth.json` 会额外保存 `hash_version` 字段，便于后续排查和兼容判断。

### Web 面板安全防护体系

当前版本实现了多层安全防护，所有安全机制（IP 过滤、封禁、防爬虫、速率限制、暴力破解防护）均完整支持 IPv4 和 IPv6 地址：

整体请求链路按公开入口和受保护内容分开处理，并统一包裹在 aiohttp 后端中间件中：`robots.txt` 在路径合法性检查后直接返回固定的 `Disallow: /` 文本，即使来源 IP 已被封禁、位于黑名单或不在白名单内，也能先看到禁止抓取规则。该端点不读取文件、不反射请求输入，也不会被 IP 封禁或 UA 指纹拦截替换成错误页；但它仍会计入匿名频率窗口，命中阈值时只记录/封禁来源 IP，不改变协议响应。登录页、登录页所需静态资源、Logo 和认证状态探测属于公开入口，但仍会经过相应的 IP/防爬虫检查。面板页、面板静态资源以及所有 `/api/*` 非公开接口必须同时满足当前 IP 可访问、JWT 真实有效、服务端会话存在且未过期，并通过对应的防爬虫/已登录速率检查后，才会返回数据或执行写入。浏览器地址栏直接访问 API 时，会先完成这些安全检查，再空响应体跳转到统一无权限错误页，不向页面渲染业务 JSON。普通页面的 400/403/404 会通过一次性错误页令牌进入统一错误页；系统跳转会停留在错误页，用户手动访问或刷新错误页时会重新按当前 IP/token 状态分流。统一错误页不做 UA 指纹重复拦截，避免拦截页循环跳转；但它固定参与匿名频率限制，并带 `X-Robots-Tag: noindex, nofollow, noarchive`，避免拦截页被搜索引擎收录。错误页的核心状态内容由后端按固定错误码渲染，前端脚本只作为增强层；`reason` 只来自服务端一次性跳转令牌，不从 URL 参数反射展示。

IP 访问控制的语义分层如下：受保护 IP 是最高优先级，永远放行且不会被封禁、速率限制或爆破锁定影响；白名单模式只允许名单内 IP 访问，白名单 IP 不写入封禁表且豁免防爬虫/已登录速率限制，但输错密码仍会走登录爆破阶梯锁定；黑名单模式直接拒绝名单内 IP；封禁表由手动封禁、防爬虫自动封禁和登录爆破封禁共用，同一 IP 只保留一条记录，重复手动封禁会更新原记录而不是生成冲突记录。

所有可被前端提交的输入都在后端重新校验：JSON 请求体必须是对象，密码/改密字段、IP 名单、封禁备注、分页参数、文件路径、文件内容和聊天记录结构都有类型、长度和范围检查。前端校验只负责即时提示，不能绕过后端安全边界。

反向代理头只在可信连接来源下参与安全判断：当后端看到的连接来源是本机回环地址时，会自动读取合法的 `X-Real-IP / X-Forwarded-For` 获取真实 IP；当反向代理部署在另一台机器上时，必须显式开启 `web_panel_trust_proxy` 才会信任代理头。可信代理场景下，`X-Forwarded-Proto` 会用于判断是否设置 Secure Cookie，`X-Forwarded-Host` 会用于同源写请求校验；Host 类头部只接受常规主机名、IP 和端口字符，异常值会被拒绝。默认不信任远程代理头是有意的安全边界，避免公网直连客户端伪造真实 IP。

Web 响应统一附加安全头，包括 `X-Content-Type-Options`、`X-Frame-Options`、`Strict-Transport-Security`、`Referrer-Policy`、`Permissions-Policy`、`Cross-Origin-Opener-Policy`、`Cross-Origin-Resource-Policy` 和 `Cache-Control: no-store` 等。登录页、面板页和错误页使用每次响应随机生成的 CSP nonce 限制脚本执行，nonce 只在本次响应内使用，不写入持久化文件。这些防护依赖标准 HTTP 头和 Python 标准库实现，不绑定特定浏览器内核或操作系统；现代 Chromium、Firefox、WebKit 都能识别主要安全头，旧浏览器即使忽略部分头部，也无法绕过后端认证、IP 校验和文件/配置接口校验。

#### 1. Content-Security-Policy (CSP)

所有页面均强制启用严格 CSP，防止 XSS 攻击注入恶意脚本：

- **script-src**：使用 **nonce（一次性令牌）** 替代 `unsafe-inline`，每个响应生成唯一 nonce 并注入到 `<script>` 标签中
- **style-src**：保留 `unsafe-inline` 以支持动态主题切换等运行时样式操作
- **default-src**：设为 `'none'`，仅允许显式声明的资源来源
- **connect-src / form-action / frame-ancestors**：限制为 `'self'` 或禁止

> 这意味着即使攻击者能在页面中注入 HTML，也无法执行任意 JavaScript 代码。

#### 2. 会话令牌与多端登录

当前 Web 面板使用 **JWT + HttpOnly Cookie + 服务端会话表** 的组合方式管理登录态：

- 登录成功后，服务端创建独立 `sid / device_id` 会话记录，并通过 `HttpOnly Cookie` 下发登录态
- 每次登录都会生成新的独立会话，因此 **多设备 / 多浏览器 / 多次登录默认允许并存，不会互踢**
- 登录页访问到有效会话时，会直接跳转到面板页，无需重复输入密码
- `web_panel_ip_bind_check=true` 时，会把登录 IP 绑定到会话中；普通请求、面板访问和心跳都会校验当前 IP
- 心跳接口只更新最近活跃时间，不会延长 24 小时绝对过期时间
- 改密码、密码重置、非 Web 面板发起的服务端重启，会让旧会话整体失效并要求重新登录
- `sessions.json` 固定保存在 `web_data/` 下，过期、撤销或长期无活动的历史会话会在启动、成功登录和后台维护任务中清理，避免旧会话记录无限堆积

#### 3. 会话心跳机制

前端会通过低频心跳主动检测会话是否仍然有效：

- 前台默认每 `300` 秒检测一次
- 后台默认每 `1200` 秒检测一次
- 页面切回前台、网络恢复时会立即补一次检测
- 网络异常时不会立即判定断联，而是进入缓冲重试期，按 `15s → 30s → 60s → 120s` 逐步退避重试
- 只有后端明确返回会话失效状态（401）时，才会统一清理会话并要求重新登录；具体失效原因只写入服务端日志，不向受保护 API 调用方暴露
- 同一浏览器多标签页只会选出一个 `Leader` 标签页负责发心跳，其余 `Follower` 标签页只监听广播，避免重复探测

#### 4. 前端页面自动刷新与手动刷新

前端在会话详情页、数据可视化页和核心设置页内置了自动刷新机制，并在关键位置提供了带反馈的手动刷新按钮。

**自动刷新（程序轮询，仍计入已登录速率窗口）：**

- **会话管理列表页**：每 **3 秒** 自动刷新会话数量和卡片数据（消息数、文件大小等）。页面头部 `自动刷新（3秒）` 开关可随时启停。进入某个会话查看详情时自动暂停，返回列表时恢复；后台标签页会跳过展示类刷新。
- **会话详情页**：每 **3 秒** 自动刷新详情数据，页面头部 `自动刷新（3秒）` 开关可随时启停。聊天记录使用**增量更新**——通过内容比对而非条数判断变化，仅追加新增消息并保持滚动位置。聊天记录区域有提示说明自动刷新可能存在延迟，建议必要时点击手动刷新。进入 JSON 编辑模式时自动暂停轮询（自动和手动刷新均不会覆盖编辑器），保存时直接覆盖源文件；后台标签页会跳过详情轮询。
- **数据可视化页**：每 **3 秒** 自动刷新，无会话时只刷新全局概览，选中会话后同步刷新详细图表。监听主题切换事件，切换亮/暗主题时立即重绘所有 Canvas 图表。页面头部 `自动刷新（3秒）` 开关可随时启停。图表刷新有防重入保护，上一轮未结束时不会叠加下一轮；慢请求期间切换会话会排队重建最新会话视图。
- **核心设置页 — 会话心跳状态**：按心跳可见间隔的一半（最小 5 秒）自动刷新，间隔随用户配置动态变化，标签动态显示实际秒数。独立 `自动刷新` 开关可随时启停（仅设标志位，**定时器持续运行不随页面切换启停**）。心跳状态展示刷新有防重入保护，并且后台标签页会跳过展示更新。心跳成功时间通过每次 verify 成功同步更新，Follower 标签页接收 Leader 的 `session-ok` 广播后同步状态。

**手动刷新（用户主动触发，走对应场景的速率审查）：**

- **会话管理列表页**：页面头部有 `刷新列表` 按钮（始终可见），点击后全量重新加载会话数据。
- **数据可视化页**：页面头部有 `🔄 刷新` 按钮（始终可见），点击后全量重建：无会话选中时只刷新全局概览，选中会话后刷新概览及该会话的详细图表。弹出 toast（"数据已刷新" / "刷新失败"）。
- **会话详情页**：页面头部有 `刷新` 按钮（始终可见），点击后刷新所有详情数据并**强制全量重载聊天记录**（编辑模式下跳过），弹出 toast（"会话数据已刷新" / "刷新失败"）。
- **核心设置 — 心跳状态**：页面头部有 `🔄 刷新` 按钮（始终可见），点击后重新获取心跳状态并弹出 toast（"心跳状态已刷新" / "刷新失败"）。
- **访问日志页**：**不提供自动刷新**（日志为安全审计数据，避免轮询掩盖实时追踪窗口）。刷新按钮左侧显示提示文字"本页无自动刷新，有新日志产生时请手动点击刷新按钮获取最新信息"，文字颜色跟随 `--text-secondary` 适配明暗主题，字号与最大宽度按桌面/平板/手机三端断点自适应。
- **文件管理页**：**不提供自动刷新**（页面性质特殊，文件内容由用户主动控制）。页面顶部显示提示横幅告知手动刷新。点击 `刷新` 按钮会同时刷新文件列表和当前打开的文件内容（如有未保存修改会先确认），并弹出 toast。

**速率审查区分：**

自动刷新请求会携带 `X-GCP-Auto-Refresh: 1` 请求头，但该头部只用于前端区分请求来源，不是后端安全豁免依据。数据图表、会话管理、心跳状态展示等自动刷新请求在令牌有效时仍计入已登录速率窗口；令牌无效、过期或不存在时，会按未认证请求进入防爬虫检测。只有 `/api/auth/heartbeat` 专用认证心跳不计入已登录速率窗口，但它仍必须通过当前 IP 可访问、JWT 真实有效、服务端会话存在且未过期等校验。

#### 5. 敏感文件保护

Web 文件管理 API 对以下敏感文件实施访问控制：

| 受保护文件/模式 | 保护原因 |
|----------------|----------|
| `auth.json` 及同名备份 | 包含密码哈希 |
| `jwt_secret.json` 及同名备份 | 包含 JWT 签名密钥 |
| `sessions.json` 及同名备份 | 包含服务端 Web 会话表 |
| `access_log*` | 访问日志可能暴露 IP 信息 |
| `bans.json` 及同名备份 | 封禁策略不应被篡改 |

这些文件不会出现在 Web 面板文件浏览器中；即使绕过前端直接调用文件读取、保存或删除 API，也会被后端拒绝。Web 会话管理中的聊天记录查看/编辑针对的是插件自定义 `chat_history/...` 历史文件，而不是这些核心安全文件。

访问日志文件固定为 `web_data/access_log.jsonl` 及其大小轮转文件 `access_log.1.jsonl`、`access_log.2.jsonl`。日志自动清理只处理这些固定文件名，不使用可由请求参数控制的路径；写入和返回日志前会清洗 IP、方法、路径和附注文本，避免把控制字符或异常长文本原样带回前端。

#### 6. Web 会话管理、重置与图片缓存边界

当前 Web 面板中有三类容易混淆的动作：

- **会话管理中的单会话重置**（Web 会话管理卡片上的「重置」按钮）
  - 仅清理该会话相关运行态（注意力、情绪、概率、冷却、处理中标记等），**不删除聊天记录文件**
  - 不设置历史截止时间戳（此为轻量操作，与指令 `gcp_reset_here` 行为不同）
  - 重置完成后自动触发插件重载使清理生效，前端轮询重载状态后自动刷新列表
  - 不扩散到其他会话
  - 如需完整重置（含截止过滤 + 文件删除），请使用「指令快捷操作 → 会话重置」功能

- **命令面板中的全局重置**（Web「指令快捷操作 → 全局重置」，对应指令 `gcp_reset`）
  - 清理插件维护的全局运行态与相关本地持久化缓存
  - 删除自定义 `chat_history` 历史目录
  - 删除注意力/主动对话等长期持久化文件
  - 为所有已知会话设置历史截止时间戳（仅过滤 `platform_message_history` 表读取）
  - **不删除** AstrBot 官方 `conversations` 表对话历史（需额外执行平台 `/reset`）

- **指令快捷操作中的会话重置**（Web「指令快捷操作 → 会话重置」，对应指令 `gcp_reset_here`）
  - 与命令行 `gcp_reset_here` 使用**完全相同的清理逻辑**（20+ 项）
  - 清理运行态 + 删自定义聊天记录文件 + 设截止时间戳

- **图片缓存清理**
  - 只清理图片描述缓存
  - 当前主缓存文件为 `image_cache/descriptions.jsonl`
  - 若检测到旧版残留路径 `image_description_cache.json`，清理逻辑也会兼容处理
  - 不清理聊天记录、注意力、概率或主动对话状态

#### 3. 默认密码日志输出机制

首次安装或密码重置后，系统会以 **WARNING 级别**向 AstrBot 日志输出默认密码及安全警告：

```
[WARNING] 🔑 Web 面板初始密码已随机生成: Abc123!xYz
[WARNING] ⚠️ 安全警告：此默认密码以明文方式暂存于 jwt_secret.json 中，
         请务必登录后立即修改为自定义密码！修改后明文副本将自动删除。
         若不及时修改，存在密码泄露风险。
```

**关键行为规则**：

| 场景 | 日志输出 | 输出级别 |
|------|---------|:--------:|
| 首次安装（初始密码生成时） | 完整密码 + 安全警告 | WARNING |
| 每次重启（用户尚未改密码） | 完整密码 + 安全警告 | WARNING |
| 用户已修改密码后 | **无任何输出** | — |
| 密码重置后 | 新密码 + 安全警告 | WARNING |
| 旧版升级（无可用的明文副本） | 通用警告，提示重置 | WARNING |

**默认密码明文的存储与清除**：
- 明文密码暂存于 `jwt_secret.json` 的 `_temp_plain_password` 字段
- 该字段仅在首次初始化/重置时写入，**用户修改密码后立即清除**
- 清除后内存和磁盘中均不再存在任何形式的明文密码

### Smart 批次回复提示增强（可选）

在 `concurrent_mode=smart` 的基础上，如果同时开启 `enable_smart_batch_reply_hint`：

- Smart 并发不仅会把”当前消息之后紧接着到达的追加消息”一起注入上下文；
- 回复阶段还会动态追加一段 `[系统提示-Smart并发]`；
- 这段提示会明确告诉 AI：当前触发对象仍是主要回复对象，追加消息仅是背景参考，直接自然说话即可，不要进行任何判断或分析；
- 这项增强只影响”怎么组织这次回复”，不会改变读空气AI在决策阶段的主体判断，也不会改写保存历史、注意力记录、最近明确回复对象等下游逻辑；
- 该提示只存在于运行时 prompt 中，保存历史前会由 `MessageCleaner` 自动过滤，不会污染普通历史正文。

### Smart 批次合并的双重上限 + 收拢延迟

数量上限（`smart_concurrent_max_batch_size`，默认 20 条）和时间上限（`smart_concurrent_merge_wait`，默认 30 秒）同时启动、各自独立、谁先触发即停止合并。`claim_batch` 是一次性快照，不会持续等待收集更多消息。

非强制消息在首次快照前有一个可配置的收拢延迟（`smart_concurrent_claim_delay`，默认 0.3 秒），用于给几乎同时到达的消息挂载 payload 的机会，减少"晚到几十毫秒就被分到下一批"的情况。当前 anchor 若已被判定为强制触发，会立即快照；吸收 follower 时，关键词触发消息作为批次边界，@AI 消息可按配置作为 follower 被吸收。

被吸收的消息在三种路径下均不会丢失：
- 决策前/claim阶段被吸收 → 内容通过 anchor 的 `_smart_batch_snapshots` 保留，anchor 回复后一并保存；
- DecisionAI 判定不回复 → 剥除特殊标记，转为普通消息缓存；
- 决策后被吸收 → anchor 自身及其 followers 均转为普通消息缓存。

⚠️ Smart 模式当前主要作用于普通消息批次合并、Smart+GWW 窗口融合以及决策/回复双阶段批次提示增强；当主动对话或冷群转正正在占用某个会话时，普通链路在读空气前、回复前和缓存转正/保存前的等待检测，仍然复用通用的 `concurrent_wait_max_loops` 与 `concurrent_wait_interval` 轮询参数，而不是切换成 Smart 专属等待逻辑。
⚠️ 选择 `concurrent_mode=smart`，不代表传统并发保护会被关闭；更准确地说，普通对话主线会优先尝试 Smart 批处理，但底层传统并发等待与兜底保护仍然存在，用来处理主动对话/冷群转正占用、等待超时回退缓存、以及 Smart 未覆盖的异常路径。

之所以不把“主回复对象”直接切换成批次中的其他人，是因为当前保存、注意力、冷却解除、最近明确回复对象等多处链路仍基于“本次主要回复对象 = 当前 event 发送者”的单主体假设。第一版保持这个假设不变，能以最小改动增强多人并发场景下的回复自然度，同时避免牵动无关逻辑。

## 一句话概括

> 本插件**完全接管了 AI 的上下文构建**，它不依赖 AstrBot 平台默认的历史消息和提示词系统，而是自己从头构建发送给 AI 的所有内容（历史消息、系统提示词、当前消息），并在最后一刻替换掉平台准备好的上下文。

## 为什么需要自建上下文？

AstrBot 平台默认的上下文构建是通用的——它把平台收到的历史消息、系统提示词、用户消息直接传给 AI。但对于一个需要"读空气"的群聊插件来说，这远远不够：

| 需求 | 平台默认行为 | 本插件的做法 |
|------|-------------|-------------|
| 消息格式 | 原样传递 | 以「: 」冒号为界，冒号前拼接时间戳、发送者名称和ID等系统元数据；冒号后为用户消息内容（含 @ 标签增强 `[At:ID|解析结果]`、转发解析等衍生内容） |
| 历史管理 | 平台统一管理 | 插件自己存储，可独立清除、截断 |
| Bot 自己的回复 | 混在历史中 | 标记为 `【禁止重复-你的历史回复】` |
| 未回复的消息 | 不区分 | 标记为 `【📦近期未回复】`，提供上下文 |
| 单独无信息@消息场景 | 平台无法区分“只是叫出来”还是“想续上文” | 默认启用最近上下文强化，并在通过读空气筛选后按最近明确回复对象给出中性提醒；内部又区分 `contains_ai`（只要空消息里包含@AI就算叫出AI）与 `only_ai`（只能是纯@AI，可重复，不能混他人/全体）两种判定语义 |
| 当前消息 | 与历史混在一起 | 用分隔线明确区分"历史"和"当前" |
| 转发消息 | 仅保留平台原始 Forward 结构/占位 | 在进入上下文前优先解析为单条可读文本，兼容 QQ / OneBot 的嵌套转发；转发内部的引用、图片、视频、语音、文件等消息段按原位置输出，无法识别的单个媒体段只在当前位置保留对应失败占位 |
| 系统指令 | 平台注入 | 插件注入自己的读空气/回复指令 |
| 窗口缓冲消息 | 不支持 | 等待窗口收集的后续消息单独标注 |
| Smart 批次回复提示 | 无 | Smart 模式下可选地动态提示 AI：主回当前对象，并自然顺带回应批次中的其他消息；该提示只存在于运行时，保存前自动过滤 |

## 核心架构：标记 → 传递 → 拦截 → 替换

整个机制可以用四个字概括：**"偷天换日"**。

> 但当前版本的“换日”并不是靠单一字符串替换硬顶到底，而是采用**优先复用旧成功路径 + 轻量兼容增强 + 失败时保守回退**的方式：能稳定识别时继续按原逻辑清理平台重复注入，识别失败时则优先保证回复链不断、其他插件内容尽量保留，并通过日志显式提示当前处于兼容回退模式。

## 什么被替换了？什么被保留了？

### 被完全替换（平台原始内容被丢弃）

| 内容 | 平台原始值 | 插件替换为 |
|------|-----------|-----------|
| `req.prompt` 主体 | 用户发送的短消息 | 插件格式化的**完整上下文**（历史+指令+当前消息），再合并第三方 prompt 安全补充（逐插件 `[第三方插件补充 - 插件名]` / `[第三方插件补充 - 插件名 结束]` 首尾配对标记，外层 `[第三方插件补充信息]` 包裹） |
| `req.contexts` 主体 | 平台对话历史数组 | 插件自己的 contexts 策略值（普通回复通常为空），再合并逐插件追踪提取的第三方安全上下文（`req.contexts` 注入型插件的伪造对话、伪工具调用等，逐插件 `[第三方插件注入上下文 - 插件名]` / `[第三方插件注入上下文 - 插件名 结束]` 首尾配对标记） |
| 平台 LTM 群聊历史 | “You are now in a chatroom...”（注入到 system_prompt 或 prompt，取决于平台配置） | **删除**（system_prompt 路径：精确条目格式匹配剥离；prompt 路径：header + 条目格式双重条件检测过滤。两条路径覆盖两种注入模式，被插件自己的历史替代） |

> 注意：这里说的是”主体语义被接管”。当前版本不再简单地把第三方对 `req.prompt` / `req.contexts` 的所有改写都一起抹掉；**正常运行时**通过逐插件追踪给每个插件的内容打上独立的名字标记（如 `[第三方插件补充 - 插件名]`）；**极少数情况下**（比如你在 Web 面板单独重启了某个其他插件）会自动降级为笼统标记（不标插件名，但仍保留内容）。
>
> 两种模式的详细说明和触发条件见 [逐插件追踪：正常模式和降级模式](#逐插件追踪正常模式和降级模式)。

### 被合并（平台与插件内容共存）

| 内容 | 处理方式 |
|------|----------|
| `req.func_tool` | 由 `reply_handler` 通过 `event.request_llm(tool_set=...)` 传递全平台工具集（含第三方 @llm_tool、平台内置工具、MCP 工具等）；`on_llm_request` 钩子只读不写，由其他插件（如 maid_agent）自由管控。工具提醒基于最终 `req.func_tool` 生成，仅做文本提示，不拦截实际工具调用；`skills_like` 模式下只展示名称/描述，`full` 或旧版配置下保持完整参数展示 |

### 被保留（其他插件的贡献不受影响）

| 内容 | 来源 | 保留方式 |
|------|------|----------|
| 向 `system_prompt` 前置的内容 | 满足条件①的插件 | 前置部分作为 prefix，SystemPromptRewriter 识别人格边界后原样保留 |
| 向 `system_prompt` 后置的内容 | 满足条件②的插件 | 后置部分作为 suffix，SystemPromptRewriter 识别人格边界后原样保留 |
| 向 `req.contexts` 注入的伪造对话/协议消息 | 满足条件③的插件 | 逐插件追踪提取，每个插件独立 `[第三方插件注入上下文 - 插件名]` / `[第三方插件注入上下文 - 插件名 结束]` 首尾配对标记 |
| 向 `req.prompt` 前后追加的长期说明/记忆文本 | 满足条件④的插件 | 逐插件追踪提取，每个插件独立 `[第三方插件补充 - 插件名]` / `[第三方插件补充 - 插件名 结束]` 首尾配对标记 |
| 向 `req.contexts` 注入的伪工具调用 | 满足条件③的插件 | 结构特征识别后追加回最终 contexts |
| `extra_user_content_parts` 中的额外块 | 满足条件⑤的插件 | 原样保留；只过滤严格识别为平台 GroupChatContext 的重复群聊历史块 |
| 人格设定 | AstrBot 平台 | 作为 `system_prompt` 基础 |
| `extra_user_content_parts` 中的额外块 | 支持该字段的第三方插件 | 保持原样，不被本插件清空；若识别规则不确定，优先保留而不是删除 |
| 人格设定 | AstrBot 平台 | 作为 `system_prompt` 基础 |

### 🆕 v1.2.2-hotfix.1+ 提示词缓存优化

插件现已将大型静态系统指令（`SYSTEM_REPLY_PROMPT`、`SYSTEM_DECISION_PROMPT` 等）追加到 `system_prompt` 中，以提高 AI 服务商的整块缓存命中率。

| AI 调用路径 | 优化方式 | 说明 |
|---|---|---|
| Tier 1（直连 `provider.text_chat()`） | 静态指令搬入 `system_prompt` | DecisionAI.should_reply()：`SYSTEM_DECISION_PROMPT` 从 `prompt` → `system_prompt` |
| Tier 2/3（钩子调用） | 静态指令追加到 `system_prompt` 末尾 | 通过 `PLUGIN_CUSTOM_STATIC_INSTRUCTIONS` extra 传递，`on_llm_request` 钩子在 SystemPromptRewriter 合并后追加 |
| 安全网 | `prompt` 保留一行兜底指引 | 钩子失败时 AI 仍能从 system_prompt 获取完整指令，prompt 中仅保留 `[请严格遵循 system prompt 中的指令进行回复]` 一行提示 |

> 对不支持缓存的 AI 服务商：发送内容实质不变，仅位置调整，不影响 AI 理解。

**保留机制的原理**：插件对平台 LTM 的剥离有两条独立路径覆盖两种注入模式——**system_prompt 路径**（Normal 模式）通过正则模式表精确匹配 LTM 条目格式剥离注入到 system_prompt 末尾的群聊历史；**prompt 路径**（Active Reply 模式）在差分提取第三方 prompt 补充时，对候选文本进行双重条件检测（必须同时命中 header 短语 + LTM 条目格式 `[昵称/HH:MM:SS]:`），满足条件即判定为平台 LTM 文本并丢弃。两个路径互为冗余：其一失效不导致另一失效。

若平台对 persona 包装或换行做了轻微调整，则退到轻量归一化识别；若仍无法高置信度识别，就进入**保守兼容模式**：优先保留当前 `req.system_prompt`，只在必要时补回插件 persona，并输出 warning 日志提醒可能存在重复提示词。对第三方写入 `req.prompt` / `req.contexts` 的内容，先走逐插件追踪；随后即使追踪已有结果，也会再用快照差分做一次残余兜底，用来覆盖热加载、加载顺序或包装失败导致的遗漏。无法确认是安全长期补充时宁可跳过，不把运行时脏内容混入 AI 输入；`extra_user_content_parts` 则相反，除非严格识别为平台 GCC 重复块，否则全部保留。默认情况下，插件自己的 persona 仍然作为 `system_prompt` 基础放在前面，其他插件附加内容尽量完整保留在后面；这样既最大限度维持旧版效果，又能在未来 AstrBot/第三方插件提示词结构变化时优先保证**主回复链不断、其他插件内容尽量保留、问题可排查**。

### system_prompt 兼容增强与保守回退机制

当前版本对 `system_prompt` 的处理分成三层：

1. **精确命中优先**  
   如果插件自己传入的人格 prompt 能在当前 `req.system_prompt` 中精确找到，就继续按旧逻辑处理；只是额外尝试保留 persona 前后的插件追加内容顺序。

2. **轻量兼容识别**  
   如果精确命中失败，会尝试基于 AstrBot 当前常见的人格包装结构（如 `# Persona Instructions`）做**弱归一化识别**：只兼容空白和换行的轻微变化，不做激进模糊匹配，避免误删其他插件内容。

3. **第三方长期注入吸收**  
   在保持本插件 full prompt / contexts 主导权不变的前提下，再额外扫描第三方在本插件之前写入的 `req.prompt` / `req.contexts`：
   - `req.prompt`：只有能从“短消息基线”里识别出的前缀/后缀型长期说明、记忆文本才会被吸收
   - `req.contexts`：只有结构稳定、能判定为长期记忆型 / fake tool call 型的上下文才会被保留
   - 吸收后的 prompt 文本会统一进入一个固定兼容补充区，并为每一段打上边界标记，避免不同插件提示词混在一起
   - 无法确认安全性的第三方改写会被跳过，并记录 warning

4. **保守回退**  
   如果仍然无法高置信度识别 persona / 平台 LTM 片段，就进入保守兼容模式：
   - 优先保留当前 `req.system_prompt`
   - 尽量不删未知结构的大段文本
   - 只在确定缺失插件 persona 时补回
   - 输出 warning 日志，提示当前可能保留了重复提示词

这意味着：
- **成功路径的语义保持不变**，仍然是“插件 full prompt + 插件 contexts 策略 + 合并后的 system_prompt”。
- **失败路径也不会炸链路**，最差退化为“可能重复，但仍能正常回复”。
- 这是一种**增强版兼容**，不是“万能兼容所有 `on_llm_request` 修改”的承诺。

**如何排查是否进入了回退模式？**
- 开启 `enable_debug_log`：可以看到本次 `system_prompt` 重写采用了哪种策略。
- 未开启 debug 时，如果进入低置信度保守模式，日志仍会输出 warning，说明当前存在平台或第三方插件提示词结构变化，插件已优先选择“不断链”的保守处理。

### 消息保存时的清洗

消息在保存到自定义存储和 `platform_message_history` 表前，会经过 `MessageCleaner` 清洗，**移除系统提示词**；若清洗结果只因首尾空白被折叠成空字符串，则保留原始空白正文，避免把“只剩空白但仍非空”的消息误删。正常转正路径（`save_to_official_conversation_with_cache`）和冷群转正路径（`flush_cached_messages_by_params`）均通过 `prepare_cache_for_save` 处理普通缓存消息；冷群转正还会通过 `prepare_window_buffered_for_save` 一并将窗口缓冲消息按时间戳合并转正。普通回复 Phase-2 只转正当前发送者当前 `gww_token` 对应的窗口缓冲消息，冷群转正才会全量合并静默遗留的窗口缓冲。所有路径均保留发送者元数据（`sender_id`、`sender_name`、`message_timestamp`、`group_id`、`group_name`、`group_role`），确保写入自定义存储、`platform_message_history` 表和 `conversations` 表时发言人信息正确。缓存转正写入 `platform_message_history` 时还会用缓存消息的稳定 `message_id` 生成 `llm_checkpoint_id` 做精确去重，避免普通回复、主动对话成功转正和冷群转正在极端并发/重试下重复写入同一条缓存消息；如果目标平台不支持该字段，则自动降级为普通写入。

系统提示词分为三类，处理方式不同：

1. **运行时内容**（`===` 分隔线、背景信息块、决策AI提示词、`[系统提示]` 触发方式说明等）——仅参与当次生成，保存时通过 `MessageCleaner` 清除，不进入历史。
2. **消息级元数据**（时间戳、发送者、`[戳一戳事件]` 持久化文本、`@全体成员` 说明等）——拼接在冒号 `:` 之前，冒号之后为用户消息内容。保存时完整保留冒号前后的格式，确保历史消息也能区分系统元数据与用户内容。
3. **运行时附加提示**（`[戳一戳提示]`）——追加在上下文分隔符 `=====` 之外，不在消息内部的元数据或内容中。仅当前轮 AI 可见，保存时由 `MessageCleaner` 过滤规则自动移除，不进入历史。`[戳过对方提示]` 同理。

```
保存前（AI 看到的）：
  “[2026-03-13 周四 14:30:00] 张三(ID:111) [环境: 技术群(ID:456)] [群主] [系统提示]注意，现在有人在直接@你并且给你发送了这条消息，@你的那个人是张三(ID:111): 你好啊
   === 背景信息 ===
   💭 相关记忆：xxx”

保存后（存入历史的）：
  “[2026-03-13 周四 14:30:00] 张三(ID:111) [环境: 技术群(ID:456)] [群主]: 你好啊”
```

> **环境标注**由 `include_environment_info` 控制，`[群主]` 等角色标签由 `enable_group_role_display` 控制——两者均属于消息级元数据，保存在冒号前。系统提示词（`[系统提示]` 等运行时内容）在保存时由 MessageCleaner 移除。

运行时内容（`=== 背景信息 ===` 等和 `[系统提示]...`）在保存时被清除；消息级元数据（时间戳、发送者等，在冒号前）和用户消息（冒号后）保留。**`[系统提示]` 触发方式说明是运行时提示词**，保存时由 `MessageCleaner` 过滤规则剥离——因为”有人在@你”只对当次回复有意义，写入历史会误导后续 AI。下次读取历史时，AI 可通过冒号明确区分系统信息与用户内容。

**戳一戳场景示例**：

```
保存前（AI 看到的上下文）：
============================================================
=== 【重要】以下是当前新消息（请优先关注这条消息的核心内容）===
============================================================
[2026-03-13 周四 14:30:00] 李四(ID:222) [戳一戳事件]有人戳了你，发起者是李四(ID:222): [ComponentType.Poke]
============================================================

[戳一戳提示]有人在戳你，戳你的人是李四(ID:222)

保存后（存入历史的）：
[2026-03-13 周四 14:30:00] 李四(ID:222) [戳一戳事件]有人戳了你，发起者是李四(ID:222): [ComponentType.Poke]
```

- `[戳一戳事件]` 在冒号前的系统元数据中，保存时保留 ✓
- `[ComponentType.Poke]` 是真实 Poke 组件的用户内容占位，用于处理平台侧空正文的戳一戳 notice ✓
- `[戳一戳提示]` 在 `=====` 分隔符之外，保存时由 `MessageCleaner` 过滤掉 ✓
- 决策AI和回复AI均能从完整上下文中看到 `[戳一戳提示]`，但该提示不写入历史

> **Web 面板会话展示说明**：
> - 「会话管理」与「数据可视化」中的会话列表，统一以复合 `chat_key`（`{platform}_{chat_type}_{chat_id}`，如 `aiocqhttp_group_123456789`）作为 canonical 会话 ID。
> - 插件自定义存储 `chat_history/...` 的聊天记录文件与当前运行时状态（注意力/情绪/概率/缓存等）按 chat_id 匹配后合并到同一个 canonical 条目下。
> - 不同平台的同一 chat_id（如 `aiocqhttp_group_123456789` 和 `gewechat_group_123456789`）会正确拆分为两条独立记录。
> - 官方 `platform_message_history` 仍会同步写入，并在部分场景作为历史读取回退来源，但它不应在 Web 面板里被展示成另一条独立会话。
> - `POST /api/session/clean-ghosts` 可清理无运行时状态的孤立聊天记录文件；前端会话管理页有对应的”清理孤立记录”按钮。

> **一次性系统提示词的保存策略**：以下提示块属于运行时 prompt，不属于应当持久化的历史内容。每个块都包裹在首尾配对的边界标记中；若极端情况下混入保存链路，`MessageCleaner` 与 `ContextManager` 的清理阶段会整块过滤：
> - `[系统-Skills开始]...[系统-Skills结束]` — Skills 提示词
> - `[系统-工具调用指引开始]...[系统-工具调用指引结束]` — 工具调用行为指引
> - `[系统提示-工具提醒开始]...[系统提示-工具提醒结束]` — 工具列表提醒
> - `[系统-情绪提示开始]...[系统-情绪提示结束]` — 情绪参考提示
> - 第三方插件注入标记（`[第三方插件补充信息]` / `[第三方插件注入上下文]` 及其逐插件具名变体）
>
> 孤儿标记（不成对的开始或结束标记）也会被单独清理，防止部分残留。
>
> **skills_like 兼容策略**：当 AstrBot 当前会话使用 `provider_settings.tool_schema_mode=skills_like` 时，工具提醒自动降级为仅展示工具名称与功能描述，不再提前展开参数列表，以尽量避免干扰框架的两阶段工具 schema 暴露流程；若当前为 `full` 模式或旧版 AstrBot 未提供该配置，则维持完整展示。

> **受保护的标记**：以下标记在清洗时会被**保留**，不会被移除：
> - `[PROACTIVE_CHAT]` — 主动对话标记，帮助 AI 理解自己主动发起的对话
> - `[🎯主动发起新话题]` / `[🔄再次尝试对话]` — 主动对话场景标记
> - `[工具调用记录开始]...[工具调用记录结束]` — 多工具调用的交错记录（每个工具独立一个块）。工具调用的参数和结果保存长度可通过 `tool_call_max_args_length`（默认5000字符）和 `tool_call_max_result_length`（默认10000字符）配置。支持完全省略（0）、自定义截断（正数，超出部分截断并添加"..."）、或完全不限制（-1，真正无上限）
> - `[追加消息上下文]` — 窗口缓冲消息标记，表示该回复生成时已参考了随后收到的追加消息（这些消息在历史中排在回复之后，但实际在回复之前收到）

## 并发处理机制（v1.2.2+）

### 两种并发处理模式

通过 `concurrent_mode` 配置可以切换两种并发处理策略：

#### legacy 模式（默认）

同一群聊同时收到多条消息时，新消息等待旧消息处理完再依次独立处理，每条消息各自调用 AI 并各自回复。

```
消息A → 处理中（6-8秒 AI 调用）→ 回复A
消息B →     等待中...         → 等待完成 → 处理消息B → 回复B
```

特点：简单可靠，向后兼容，但可能产生重复感（用户发了两条消息，AI 依次回复了两次，内容可能重叠）。

#### smart 模式

smart 模式会先登记真实到达顺序，再由最早到达的消息担任 anchor。anchor 在进入读空气 AI 前执行一次性快照，吸收已经完成前置处理且可合并的后续消息；被吸收的 follower 标记为 consumed，不再独立进入 DecisionAI 或默认 LLM 处理。

```
消息A(先到) -> arrival_seq=1 -> 完成前置处理 -> attach_payload
消息B(后到) -> arrival_seq=2 -> 完成前置处理 -> attach_payload
    ↓
A 成为 anchor
    -> 决策前 claim_batch 吸收 B
    -> B 标记为 consumed
    -> DecisionAI / ReplyAI 同时看到 A + 追加消息B
    ↓
统一生成一次回复
消息B 的处理协程：检测到 consumed -> 直接返回（不重复调用 AI）
```

特点：避免重复感，更符合人类对话习惯；`claim_batch` 是一次性快照，达到 `smart_concurrent_max_batch_size` 后停止吸收，剩余消息留给下一批次，不会和上一批继续混在一起。追加消息区域复用群聊等待窗口（GWW）的展示增强逻辑：基础 `@` 解析会展开为 `[At:ID|解析结果]`，重复 @AI、`@AI + @他人`、`@全体` 等结构会按各自消息独立保留，`@全体` 会补充说明，持久化戳一戳事件文本也会一并显示给 AI；平台侧空正文的真实 Poke 组件会以 `[ComponentType.Poke]` 占位参与保存。但运行时的主消息专用 `[系统提示]` / `【@指向说明】` 仍不会被硬塞进追加消息区。

### 主动对话与普通对话的协调（v1.2.2-hotfix.1+）

#### 普通对话冷静期（`proactive_normal_reply_cooldown`）

AI 通过普通对话流程回复了群里某人后，在 `proactive_normal_reply_cooldown`（默认 60 秒）内，主动对话系统不会触发新的主动发言。

**解决的问题**：旧版本中，主动对话计时器只看 `last_bot_reply_time`（无论是主动还是普通回复），因此 AI 刚刚正常回复完用户消息，仍可能立刻触发主动发言，造成「刚聊完又来找话说」的奇怪体验。

#### 吐槽系统感知普通活跃度（`generate_complaint_prompt`）

吐槽系统在生成吐槽文案时，会感知近 10 分钟内是否有过普通对话回复：

| 情况 | 策略 |
|------|------|
| 普通对话活跃（近 10 分钟内有普通回复） | 轻/中度吐槽概率 ×0.5，强烈吐槽概率 ×0.7；文案改为「感觉大家都在聊但没来找我」 |
| 普通对话不活跃（群里真的没人聊） | 原有文案：「连续主动说了 N 次都没人回」 |

**解决的问题**：旧版本中，AI 刚刚通过普通流程回复了很多人，然后主动对话触发了吐槽（连续 N 次无人回应），结果 AI 抱怨「群里没人理我」，与实际情况矛盾。

## 并发处理机制

### 两种并发处理模式

通过 `concurrent_mode` 配置可以切换两种并发处理策略：

#### legacy 模式（默认）

同一群聊同时收到多条消息时，新消息等待旧消息处理完再依次独立处理，每条消息各自调用 AI 并各自回复。

```
消息A → 处理中（6-8秒 AI 调用）→ 回复A
消息B →     等待中...         → 等待完成 → 处理消息B → 回复B
```

特点：简单可靠，向后兼容，是最兜底的并发保护模式；但可能产生逐条回复的重复感。

#### smart 模式

smart 模式不再按“谁先跑到某个异步点”决定主消息，而是先为消息登记到达顺序，再让最早到达的消息担任 anchor。anchor 在进入读空气 AI 前吸收后续已准备好的消息，DecisionAI 与 ReplyAI 看到的是同一批上下文。

```
消息A(先到) -> arrival_seq=1
消息B(后到) -> arrival_seq=2
    ↓
A 成为 anchor
    -> 决策前吸收 B
    -> B 标记为 consumed
    -> DecisionAI / ReplyAI 同时看到 A + 追加消息B
    ↓
统一生成一次回复
```

追加消息区域沿用窗口缓冲消息的上下文表达方式：这些消息位于当前消息之后，可能来自不同用户；若 `include_sender_info` / `include_timestamp` 开启，则会保留对应的发送者与时间信息。这里复用的是 `format_context_for_ai(window_buffered_messages=...)` 的展示入口，而不是要求 Smart follower 进入 GWW 窗口缓存；Smart follower 的完整 `cached_data` 保存在 `_smart_batch_snapshots` 中，只要传入追加消息列表，DecisionAI 与 ReplyAI 就会看到该区域，GWW 开关关闭时也不影响 Smart 自身展示。若 Smart 批次同时关联了多个 GWW 等待窗口，追加消息区域会按融合组读取这些窗口内的消息并按时间线排序，DecisionAI 与 ReplyAI 看到的是同一份批次视图。

### Smart 与群聊等待窗口（GWW）的关系

- GWW 负责”同一用户短时间拆分消息”的补收集
- Smart 负责”同群多条并发消息按真实顺序批处理”
- 两者**可以协作，但互不依赖**
- 即使不开 GWW，Smart 也能独立工作
- 进入 GWW 的消息不会再进入 Smart 批处理流程
- Smart 自己的批次快照不属于普通缓存或 GWW 窗口缓存，正常情况下只由当前 anchor 的普通回复链路读取、展示和保存；主动对话不会读取这份临时快照
- 若 Smart 批次最终需要回退（例如读空气判定不回复或会话 owner 占用超时），才会显式剥除运行时标记并转为普通缓存，后续行为与普通未回复缓存一致

Smart 与 GWW 同时开启时，如果 anchor 和被吸收消息各自带有等待窗口令牌，插件不会改写原始 `gww_token`，而是为本次 Smart 批次涉及的窗口打一个运行时融合标记。后续读取窗口上下文、追加消息计数、读空气不回复后的窗口回落、普通回复 Phase-2 保存与清理都会优先按该融合标记精确处理。未带融合标记的普通窗口继续走原有 `sender_id + gww_token` 逻辑；已有其它融合标记的窗口不会被新的批次覆盖，避免跨批次污染。

若被 GWW 或 Smart 吸收的消息本身是平台唤醒消息，插件会只消费该条事件的 AstrBot 默认 LLM 兜底，防止同一条消息在已被插件缓存/合并后又触发平台默认回复。这个事件标记不参与 Smart claim、窗口读取、回落、保存或清理；这些操作仍只使用 `processing_id`、`arrival_seq`、`sender_id`、`gww_token` 与显式融合组来定位消息。

### 等待窗口令牌绑定与回落机制（v1.2.2-hotfix.1+）

每个等待窗口创建时分配唯一递增令牌（`gww_token`）。窗口期内被拦截的每条消息将携带该令牌写入缓存。当锚点消息经读空气AI判定”不回复”后，`convert_window_buffered_to_regular` 按三层过滤精确转换该窗口批次的 `window_buffered=True` 消息为普通缓存：

| 过滤层 | 键 | 作用 |
|--------|-----|------|
| 会话隔离 | `chat_id` | 不同群聊/私信互不影响 |
| 用户隔离 | `sender_id` | 仅转换当前窗口所属用户的消息 |
| 窗口批次隔离 | `gww_token` | 同一用户多个并发窗口之间令牌不同，互不污染 |
| Smart 融合组隔离 | `gww_merge_group_id` | 仅在 Smart 批次明确标记的窗口间生效，用于统一读/转/存/清同一批窗口消息 |

回落后的消息与普通缓存行为完全一致：参与 Phase-1 转正、冷群转正、按原始时间戳统排顺序。这彻底消除了旧窗口消息残留 `window_buffered` 标记导致的下次回复上下文顺序错乱问题。Smart 批次的回落（`_smart_batch_snapshots` → `pop("window_buffered")` / `pop("smart_batch_dynamic_hint")` / `pop("gww_merge_group_id")` → 注入缓存）与 GWW 窗口回落分别处理各自的消息来源，互不干扰；若当前 Smart 批次存在融合组，GWW 回落会按 `gww_merge_group_id` 一次性转换该组内全部窗口缓冲消息，并在转普通缓存时移除融合标记，避免运行时标记进入普通缓存。

### 普通对话 / 主动对话 / 冷群转正 的互斥

群聊内部现在有一层会话级 flow owner 协调：

- `normal`：普通对话回复链
- `proactive`：主动对话链
- `idle_flush`：冷群缓存自动转正链

规则：
- 已经拿到 owner 的链路先完成，其他链路等待释放；普通消息不会在主动对话或冷群转正已经占用会话时强行抢跑
- 普通链路会在读空气前等待主动/冷转正 owner，避免基于尚未落库的主动回复做过时判断；等待超时则把当前消息回退为普通缓存，不生成、不保存 AI 回复
- 主动对话开始前会检查普通对话、普通流程意图、活跃等待窗口和其他 owner；若会话忙，会按通用并发参数短暂等待，释放后重新执行主动触发判断，不满足条件就跳过本轮；等待后仍忙也直接跳过本轮，下一次定时周期会重新读取上下文并重新预判断
- 冷群转正只在普通处理、主动对话、Smart pending 和已有 owner 都空闲时执行；成功占用后再保存普通缓存和遗留窗口缓存，保存失败或占用冲突时只跳过本轮，不清缓存
- 这是内部强制生效的实现，不新增配置项；如果未开启主动对话或冷群转正，则相关互斥逻辑不会实际介入

### 动态提示词与历史清理

Smart 追加消息、普通回复多用户提醒、主动对话预判断中的时机说明，均采用**动态注入**：

- 不直接写死到总系统提示词常量中
- 只在对应场景发生时才拼接
- 保存用户消息 / AI 回复 / 缓存转正时会统一通过 `MessageCleaner` 清理
- 不影响图片转文字 AI 及其相关配置语义

## 决策 AI vs 回复 AI：两条独立的 AI 调用路径

本插件有**两次独立的 AI 调用**，它们走完全不同的路径：

```
┌──────────────────────────────────┐   ┌──────────────────────────────────┐
│     决策 AI（"读空气"）          │   │     回复 AI（"生成回复"）        │
├──────────────────────────────────┤   ├──────────────────────────────────┤
│                                  │   │                                  │
│ 调用方式：                       │   │ 调用方式：                       │
│   provider.text_chat()           │   │   event.request_llm()            │
│   ↑ 直接调用 AI 提供商           │   │   ↑ 走平台标准流程               │
│   ↑ 不经过任何 Hook              │   │   ↑ 经过 Hook 链                 │
│   ↑ 不受其他插件影响             │   │   ↑ 受本插件 on_llm_request 拦截 │
│                                  │   │                                  │
│ 系统提示词：                     │   │ 系统提示词：                     │
│   人格设定（可选）               │   │   人格设定 + 其他插件内容        │
│   + 内置的决策判断指令           │   │   + 回复指令（静态行为规范）     │
│   + decision_ai_extra_prompt     │   │   + reply_ai_extra_prompt        │
│   （注意/情绪/疲劳等动态信息     │   │   + 工具提醒 + 情绪参考（动态） │
│    在用户提示词中注入）          │   │                                  │
│                                  │   │                                  │
│ 上下文：                         │   │ 上下文：                         │
│   近期消息摘要（较短）           │   │   完整格式化历史（完整）         │
│                                  │   │   + 记忆 + 工具 + 窗口消息      │
│                                  │   │                                  │
│ 输出：                           │   │ 输出：                           │
│   YES / NO                       │   │   AI 的回复文本                  │
│                                  │   │                                  │
│ AI 提供商：                      │   │ AI 提供商：                      │
│   decision_ai_provider_id        │   │   AstrBot 默认提供商             │
│   （可单独配置轻量模型）         │   │                                  │
│                                  │   │                                  │
└──────────────────────────────────┘   └──────────────────────────────────┘
```

### 私信链路的对应关系

私信模块虽然仍处于开发测试阶段，但 AI 调用类别与群聊主链路保持同类对齐：

- **私信回复生成**：与群聊回复生成一样走 `event.request_llm()`，先传短消息/占位 prompt，再由 `on_llm_request` 恢复完整上下文
- **私信主动对话生成**：与群聊主动对话一样走 `ProviderRequest + OnLLMRequestEvent + provider.text_chat()` 这条兼容链路
- **私信图片转文字**：与群聊图片转文字一样保持 `provider.text_chat()` 直连，不进入回复 Hook 链

也就是说，这里并不是把所有 AI 调用统一成一种方式，而是让**每一类 AI 继续走它本来对应的那条链路**。

---

### 决策 AI / 回复 AI 的最近上下文增强

除了原本的完整历史上下文外，当前实现还额外引入了两层“最近上下文”增强，但它们彼此解耦：

1. **普通概率路径的注意力冷却补丁**
   - 只作用于非@AI、非关键词触发的普通概率路径消息
   - 当一条消息看起来不是发给AI时，不会立刻把高注意力用户推进正式冷却，而是先进入“未接续谈保护”（pending reconnect）
   - 未接续谈保护只观察**同一用户自己的后续消息**，不受群里其他人插话干扰
   - 如果该用户紧接着又发普通消息，系统会给他一个最低概率保护，减少“上一条没接住，下一条普通消息也被一起误伤”的情况
   - 如果该用户已经不在当前会话的注意力追踪列表中，则其 pending / active 冷却状态会被同步移除，不再继续推进到正式冷却
   - “读空气未回复衰减”已从冷却本体中解耦：未开启冷却时可独立生效；开启冷却时，只有正式冷却后才执行一次注意力衰减
   - 冷却状态改为运行态内存数据，插件或平台重启后会自然清空，不再长期持久化

2. **单独的、不包含任何信息的 @ 消息默认上下文强化**
   - 只在“仅@AI且没有文字/图片/关键词等其他内容”时触发
   - 不依赖注意力冷却状态，而是独立参考“最近一次明确回复对象”
   - 系统会先走完前置过滤与读空气筛选，只有最终决定回复时，才在回复阶段追加这层提醒
   - 若当前发送这条消息的人与最近一次明确回复对象相同，且仍在关联窗口内，则给AI一段**中性**提示：优先参考最近上下文，但不要强行续话
   - 若不是同一人，或时间 / 消息数任一窗口超限，则降级为更中性的自由判断提示
   - 关联窗口阈值默认启用，可通过 `single_at_message_reply_link_max_messages` 与 `single_at_message_reply_link_max_seconds` 配置；两者会同时生效

这意味着：
- **读空气AI** 不会被这层提醒提前干扰，仍只负责判断该不该回
- **回复AI** 会在真正需要回复时更自然地参考最近上下文，但不会死盯上一段历史
- 这层机制只是“回复阶段的增强判断线索”，不会把 AI 锁死在必须续接上文的行为里
- 当 `concurrent_mode=smart` 且开启 `enable_smart_batch_reply_hint` 时，回复阶段还会动态追加一段 `[系统提示-Smart并发]`，提醒 AI 主回当前对象，并可自然顺带回应批次中的其他消息
- 这类 Smart 提示同样属于运行时 prompt，会在保存前自动过滤，不会进入普通历史正文

## 🆕 AI 错误处理机制：智能识别与零副作用跳过

### 核心设计理念

当 AI 调用失败时（如服务商 502、网络超时等），系统应**明确区分「外部故障」和「代码问题」**，并确保**错误不会触发任何副作用**（打分/概率调整/冷淡期/沉默计时器重置）。

### 错误格式化器 (`ai_error_formatter.py`)

所有 AI 调用的异常都通过 `format_ai_error()` 统一处理，自动识别 5 类错误：

| 错误类型 | 识别特征 | 日志输出 |
|---------|---------|---------|
| **HTML 网关错误** (502/503/504) | 响应体包含 `<html>` / `cloudflare` / `Bad Gateway` 等 | `⚠️ AI 服务商故障 HTTP 502：... → 这不是插件代码的问题` |
| **上游模型空输出** | 包含 `upstream_empty_output` / `empty output` / `no usable output` 等关键词 | `⚠️ 上游模型返回空输出：模型/中转接口这次没有返回可用内容` |
| **HTTP 状态码错误** (400-599) | 异常信息包含标准状态码 | `⚠️ AI 服务商故障（HTTP 500）` 或 `⚠️ 请求参数/配置问题（HTTP 400）` |
| **网络连接问题** | 包含 `timeout` / `connection refused` / `DNS` 等关键词 | `⚠️ 网络问题（请求超时）` |
| **其他异常** | 不匹配以上模式 | 普通错误信息（超长时自动截断至 300 字符） |

### 零副作用跳过原则

以下场景中，AI 调用失败被视为**本次操作未发生**，不触发任何状态变更：

| 场景 | 影响的机制 | 处理方式 |
|------|----------|---------|
| **主动对话生成 AI 调用失败** | 打分、概率提升、冷淡期、沉默计时器 | 显式 `return`，不执行步骤 8（`record_bot_reply` + `activate_temp_probability_boost`） |
| **主动对话发送/保存阶段出错** | 同上 | 外层 `except` 仅记录日志，不触发副作用 |
| **主动对话 AI 预判断调用失败** | 沉默计时器重置 | 不更新 `last_bot_reply_time`，快速进入下一次检测 |
| **主动对话 AI 预判断超时** | 同上 | 同上 |
| **读空气（决策 AI）调用失败** | — | 返回空字符串，视为「未判断」，不影响后续流程 |
| **普通群聊回复：LLM 返回空文本** | 成功回复后的冷却解除、最近明确回复对象、AI 回复历史保存 | 不保存 AI 回复；但仍继续保存当前用户消息、待转正缓存以及窗口缓冲 Phase-2，避免上下文断裂 |
| **普通群聊回复：工具调用异常导致 Agent 异常终止** | 中间回复文本与工具调用交错记录的丢失 | `after_message_sent` 中检测到 AI 错误标记或非 LLM 终端响应附带待保存文本时，强制弹出 `_pending_bot_replies` 中的累积文本并构建交错工具调用记录保存到 ContextManager，确保工具调用出错的链路中也不漏存。注意：LLM_RESULT 类型不在此处强制完成——多轮工具调用中中间文本也是 LLM_RESULT，正常完成由 `on_llm_response` → `_agent_done_flags` 处理。 |
| **图片转文字 AI 调用失败** | — | 跳过该张图片，继续处理其余图片 |

> **对比：正常业务逻辑 vs 异常跳过**
>
> - **AI 预判断返回 `no`（判断不通过）** → 这是正常的业务结果，会更新 `last_bot_reply_time` 重置沉默计时器 ✅
> - **AI 预判断抛出 502 异常** → 这是外部故障，**不更新**任何状态 ❌→❌
> - **普通回复真正生成出文本** → 正常保存 AI 回复，并继续执行冷却解除、最近明确回复对象等成功回复副作用 ✅
> - **普通回复最终为空文本** → 视为“这次没有真正回出去”；只补做用户消息与缓存转正保存，不补做成功回复副作用 ❌→✅（仅上下文保存）

## 与其他插件的兼容性

### 消息处理链兼容性（v1.2.1+）

本插件的消息处理器（`on_group_message`、`on_private_message`）使用 **`priority=-1`**，低于 AstrBot 默认优先级（0），确保其他插件的消息处理器**先于本插件执行**。

如果其他插件（如 `better_reminder`、`llm_poke` 等）已经对当前消息发送了回复，本插件会检测到 `event._has_send_oper` 标记并**自动跳过 AI 处理**，避免重复回复。跳过时仍会将消息缓存到上下文池，确保 AI 不丢失上下文。

```
消息处理链执行顺序（AdapterMessageEvent）
═══════════════════════════════════════════════════

优先级 sys.maxsize-1   command_filter_handler（本插件）
                       ├─ 检测指令消息（/help、!reset 等）
                       └─ 标记后返回，不发送回复，不阻止传播
                           ↓
优先级 0（默认）       其他插件的消息处理器
                       ├─ better_reminder.on_message
                       ├─ self_learning.on_message（只收集数据，不发送）
                       ├─ 其他插件...
                       └─ 如果某个插件发送了回复 → _has_send_oper = True
                           ↓
优先级 -1              on_group_message / on_private_message（本插件）
                       ├─ 检查 _has_send_oper
                       │   ├─ True → 缓存消息到上下文池，跳过 AI 处理
                       │   └─ False → 正常处理（概率→读空气→回复）
                       └─ 处理完毕
```

> **注意**：AstrBot 框架在每个 handler 之间调用 `event.clear_result()`，会清除 `stop_event()` 状态。因此 `stop_event()` 无法跨 handler 传播。`_has_send_oper` 标记不受 `clear_result()` 影响，是唯一可靠的跨 handler 通信方式。

> **与 LLM 钩子链无关**：消息处理链（`AdapterMessageEvent`）和 LLM 钩子链（`OnReqLLMEvent`）使用独立的优先级排序。本插件消息处理器的 `priority=-1` 不影响 `on_llm_request` 钩子的 `priority=-1`，两者在不同的事件链中各自独立排序。

### 如何判断一个插件是否兼容

判断方法很简单：**查看该插件的 `on_llm_request` 钩子，看它往 `req` 的哪个字段、以什么方式注入了内容。** 只要匹配以下任一条件，就可以兼容。

**自查三步：**

1. **找到该插件的源码**，搜索 `on_llm_request`，看它是否注册了这个钩子。如果没有 → 兼容（条件⑦）。
2. **看它修改了 `req` 的哪些字段**（`system_prompt` / `contexts` / `prompt` / `extra_user_content_parts`），以及是**前置、后置还是新增**。
3. **看装饰器的 `priority=` 参数**：绝大多数插件是 0 或正数，在本插件之前执行 → 正常兼容；如果 < -1（极少见），则在本插件之后执行，内容可能丢失。

#### 兼容条件（满足任一即可）

| 条件 | 判断依据 | 保留机制 |
|------|---------|---------|
| ① 向 `req.system_prompt` **前面插入**了内容 | 插件代码中有类似 `req.system_prompt = xxx + req.system_prompt` 或 `req.system_prompt = f”{xxx}\n{req.system_prompt}”` 的写法 | SystemPromptRewriter 识别出人格边界后，前面的内容作为 prefix 原样保留 |
| ② 向 `req.system_prompt` **后面追加**了内容 | 插件代码中有类似 `req.system_prompt += xxx` 或 `req.system_prompt = req.system_prompt + xxx` 的写法 | SystemPromptRewriter 识别出人格边界后，后面的内容作为 suffix 原样保留 |
| ③ 向 `req.contexts` 中**新增了消息** | 插件代码中有类似 `req.contexts.append(...)` 的写法，且追加的是有 `role`/`content` 结构的 dict | 逐插件追踪提取 → 每个插件独立 `[第三方插件注入上下文 - 插件名]` / `[第三方插件注入上下文 - 插件名 结束]` 首尾配对标记 |
| ④ 向 `req.prompt` **前面或后面追加**了内容 | 插件代码中修改了 `req.prompt`，在原用户消息前后加了额外的说明/记忆文本 | 逐插件追踪提取 → 每个插件独立 `[第三方插件补充 - 插件名]` / `[第三方插件补充 - 插件名 结束]` 首尾配对标记，外层 `[第三方插件补充信息]` / `[第三方插件补充信息结束]` 包裹 |
| ⑤ 向 `req.extra_user_content_parts` **追加**了内容 | 插件代码中有类似 `req.extra_user_content_parts.append(...)` 的写法 | 原样保留，不做任何修改 |
| ⑥ 不修改 `req`（自己调用 AI） | 插件绕过 `on_llm_request`，直接用 `provider.text_chat()` 发起请求 | 互不干扰 |
| ⑦ 不注册 `on_llm_request` 钩子 | 插件不参与 LLM 请求的上下文构建 | 没有冲突 |

#### 可能冲突的情况

| 情况 | 原因 | 后果 |
|------|------|------|
| 直接整体重写 `req.prompt` | 无法从短消息基线中提取安全增量 | 该插件内容可能被跳过 |
| 塞入结构异常/字段缺失的 contexts | 差分法只吸收有 `role`/`content` 的合法 dict | 异常内容会被丢弃 |
| 有自己的 LTM/历史管理且同时注入平台历史 | 两套历史系统语义重叠 | AI 可能看到重复或矛盾的历史 |
| 本插件接管后运行时（priority < -1）才执行 | 在本插件差分快照之后才修改 req | 注入内容不会被捕获 |
| 依赖平台默认上下文格式 | 本插件主导最终 prompt/contexts 语义 | 该插件可能无法按原设计工作 |

#### 优先级风险说明

`on_llm_request` 钩子的**优先级决定了执行顺序**（数值越大越先执行）：

| 优先级 | 执行时机 | 对本插件的影响 |
|--------|---------|---------------|
| **> 0**（如 100000） | 在本插件**之前**执行 | ✅ 修改被快照捕捉，差分法正常保留 |
| **0（默认）** | 在本插件**之前**执行 | ✅ 同上，差分法正常保留 |
| **-1** | 本插件自身 | — |
| **< -1** | 在本插件**之后**执行 | ⚠️ 快照已拍完，此后的修改**不会被差分法捕获**，注入内容可能丢失 |

> **排查方法**：如果你不确定某个插件的优先级，在它的 `on_llm_request` 装饰器上查看 `priority=` 参数。未显式指定时通常为 0。绝大多数第三方插件不会使用 < -1 的优先级，所以这个风险实际很少触发。如果真的遇到了，可以联系该插件作者调整优先级，或在 debug 日志中确认是否丢失。

#### 逐插件追踪：正常模式和降级模式

别的插件往 AI 请求里塞了什么东西，本插件通过"观察壳"来识别，然后打上这个插件的名字再传给 AI。这里有两套方法在背后工作：一套是新方法（精确到具体插件名），一套是旧方法（笼统标记为"第三方插件"）。新方法优先，旧方法兜底。

##### 正常模式：你什么也不用做

插件启动时，会自动给所有其他插件的处理器加上一层观察壳。过程是这样的：

1. 每条群消息触发 AI 回复时，AstrBot 会按优先级从高到低，逐个调用你装的所有插件
2. 每个插件被调用前后，观察壳各拍一张快照，对比出这个插件往请求里追加了什么内容
3. 把追加的内容打上该插件的名字（比如 `[第三方插件补充 - LivingMemory]`），暂存起来
4. 等最后轮到本插件处理时，把这些带名字的内容整理好，放回请求里交给 AI

整个过程全自动，你不需要做任何事。

##### 降级模式：什么时候会触发

以下操作会让部分插件的观察壳丢失，插件会自动切回旧方法：

- **在 Web 面板单独重启某一个其他插件**：比如你觉得记忆插件不太对劲，去 Web 面板点了一下它的"重启"按钮。那次重启会让这个插件被 AstrBot 卸载→重新加载，旧的处理器被丢弃，新的处理器注册上来。但观察壳是在插件启动时一次性装的，不会知道有新处理器来了。

  结果：这个刚重启过的插件追加的内容仍然会被保留（旧方法兜底），只是标记会从 `[第三方插件补充 - LivingMemory]` 变成笼统的 `[第三方插件补充]`，不再标具体插件名。**不影响回复内容本身**，只是标记没那么精细了。

- **不用担心的场景**：

  | 你做了什么 | 结果 |
  |-----------|------|
  | 重启了本插件自己 | 本插件重启时会重新给所有处理器加壳，追踪完全恢复 |
  | 重启了所有插件 / 重启了 AstrBot | 等同于全新启动，全部处理器重新加壳，正常工作 |
  | 什么都没干，正常用 | 永远走正常模式，不会降级 |

##### 怎么看当前走的是哪条路

几条日志线索：

- **插件启动时**，日志里出现 `[逐插件追踪] 已包装 N 个 OnLLMRequest handlers`，说明观察壳安装成功，N 就是被加壳的其他插件数量
- **每次 AI 回复时**，如果在 debug 模式，日志里出现 `[逐插件隔离] 已使用逐插件 prompt 隔离`，说明本次请求走了正常模式（带插件名标记）
- **如果没看到"逐插件隔离"日志**（非 debug 模式下正常不会打印），说明本次走了降级模式——插件仍在工作，只是不标插件名了

> **简单记**：降级不代表出 bug，只是标记精度从"谁加的"变成"别人加的"。两种模式下其他插件的内容都会被保留，AI 都能看到，回复质量不受影响。

#### system_prompt 识别的三种路径与风险

SystemPromptRewriter 在合并 system_prompt 时有三种策略：

| 策略 | 触发条件 | 保留效果 | 风险 |
|------|---------|---------|------|
| **精确命中** (confidence=high) | 插件自己的人格 prompt 在 `req.system_prompt` 中被精确找到 | prefix + persona + suffix 完整保序 | 几乎没有风险 |
| **轻量归一化** (confidence=medium) | 平台对 persona 做了轻微包装（如 `# Persona Instructions`），仅空白/换行有差异 | 同样保序，但会输出提示告知走了归一化路径 | 极小概率误识别边界 |
| **保守回退** (confidence=low) | 无法高置信度识别 persona 边界 | 优先保留当前 system_prompt，只去掉已知 LTM 片段，补回插件 persona | **宁重复不缺漏**，可能保留部分平台注入的重复内容，但主回复链不断 |

> 如果日志中出现 `[兼容回退]` warning，说明当前 system_prompt 结构与预期有差异，插件已优先选择"不断链"。此时 AI 可能看到少量重复的平台提示词，但第三方插件的注入内容仍然会被尽量保留。

#### 平台 LTM 格式变更的风险

平台 LTM 的识别有三条独立路径，互为冗余：

1. **system_prompt 路径**（旧版 Normal 模式）：通过 `SystemPromptRewriter._strip_known_ltm()` 的正则模式表精确匹配。Pattern 1 匹配 LTM 条目格式 `[昵称/HH:MM:SS]: 内容`（条目间以 `\n---\n` 分隔，使用 `(?!---\n)` 负向前瞻支持条目内多行消息），Pattern 2 匹配 Active Reply 完整格式（含 `Now, a new message is coming:` 等）。若两个正则均不命中，后续的降级策略（conservative-keep-current / conservative-prepend-plugin）会做兜底处理

2. **prompt 路径**（旧版 Active Reply 模式）：通过 `_looks_like_known_runtime_text()` 的双重条件检测——必须同时命中 header 短语 `"You are now in a chatroom"` 且正则匹配到 LTM 条目格式 `[昵称/HH:MM:SS]:` 才判定为平台 LTM 文本。第三方插件内容无法同时满足这两条，不会被误过滤

3. **extra_user_content_parts 路径**（新版 4.25.2+，GCC 注入）：通过 L1 精确文案匹配（`"Belows are group chat context after your last reply"`）+ L2 结构特征兜底。两层都必须同时满足 `<system_reminder>...</system_reminder>` 框架、`--- BEGIN CONTEXT---` / `--- END CONTEXT ---` 分隔符，以及平台群聊记录行格式 `[昵称/HH:MM:SS]:`，才会移除。普通系统提醒、第三方 `<context>`、`<image_caption>`、情绪/偷取指令或自定义分块都不会命中；若未来平台格式变化导致识别不确定，则保留该块，最多产生重复上下文，不会误删第三方注入

三条路径覆盖了 AstrBot 平台 LTM/GCC 的三种注入模式，无论平台版本或配置如何切换均有对应的剥离逻辑。如果 AstrBot 未来版本改写了注入文案：

- **能匹配上** → 正常删除，避免与插件自建历史重复
- **匹配不上** → 正则/文本匹配失效，平台 LTM/GCC 片段被保留（system_prompt 路径进入降级策略，prompt 路径回退到 `plugin_prompt` 子串匹配兜底，extra 路径直接保留）。三条路径独立运作，单条失效不会导致其他路径也失效

> 这里的设计原则是**宁重复不缺漏**：删不掉平台历史最多让 AI 看到两份上下文（通常不影响回复质量），但误删第三方插件的注入会导致功能异常。三条路径均采用精确格式匹配（system_prompt 路径匹配条目结构，prompt 路径要求 header + 条目格式双重命中，extra 路径要求 system_reminder 框架 + begin/end 分隔符 + 平台记录行格式），确保第三方插件内容不被误伤。

```

## Hook 执行顺序详解

AstrBot 的 Hook 系统按**优先级从高到低**执行。本插件使用 `priority=-1`，确保在**最后执行**，这样它可以看到所有其他插件追加的内容，并优先按“旧成功路径 → 轻量兼容识别 → 保守回退”的顺序处理：

```
on_llm_request Hook 执行链
═════════════════════════════════════════════════

优先级 100000   向 system_prompt 后置追加的插件
                ├─ 向 system_prompt 后面追加状态规则 + 输出协议
                ├─ 向 contexts 注入伪造对话示例 + 协议强制消息
                └─ 不修改 prompt
                    ↓
优先级 0（默认）向 system_prompt 前置 / 向 prompt 注入 / 向 extra 注入 等插件
                ├─ 前置注入型: 向 system_prompt 前面插入规则块
                ├─ prompt/contexts 注入型: 向量检索后按模式注入
                │   · system_prompt 模式 → 追加记忆到 system_prompt
                │   · user_message 模式 → 在 prompt 前后追加
                │   · fake_tool_call 模式 → 向 contexts 注入伪工具调用
                ├─ extra 注入型: 向 extra_user_content_parts 注入
                │   <context> 标签
                │   回退时追加到 system_prompt
                └─ 不修改 prompt（extra 注入型主要通过 extra）
                    ↓

                │
                │  【AstrBot 版本决定注入方式和通道】
                │
                ├─ 旧版 ≤4.25.1 — LongTermMemory：
                │   │
                │   ├─ Normal 模式（enable_active_reply=False）：
                │   │   ├─ 在 system_prompt 末尾追加：
                │   │   │   "You are now in a chatroom.
                │   │   │    The chat history is as follows:
                │   │   │    [平台存储的群聊历史，格式 [昵称/HH:MM:SS]: 内容]"
                │   │   ├─ 设置 req.contexts = [平台对话上下文]
                │   │   └─ 不修改 prompt
                │   │
                │   └─ Active Reply 模式（enable_active_reply=True）：
                │       ├─ 在 req.prompt 中包裹：
                │       │   "You are now in a chatroom. The chat history is as follows:
                │       │    [平台存储的群聊历史]
                │       │    Now, a new message is coming: `{用户消息}`.

                │       ├─ 清空 req.contexts = []
                │       └─ 不修改 system_prompt
                │
                └─ 新版 ≥4.25.2 — GroupChatContext：
                    │
                    └─ 统一注入到 req.extra_user_content_parts：
                        ├─ 注入格式：
                        │   "<system_reminder>
                        │    You are in a group chat.
                        │    Belows are group chat context after your last reply:
                        │    --- BEGIN CONTEXT---
                        │    [平台存储的群聊历史，格式 [昵称/HH:MM:SS]: 内容]

                │     L2 "group chat" + system_reminder 框架 + begin/end 分隔符 + 记录行
                │         （结构特征兜底，宁可保留重复也不误删）
                │     → 移除 GCC 注入的群聊历史块
                │     → 第三方注入的 extra parts 不受影响（不命中 L1/L2）
                │
                └─ 10. 清除 event.extra 中的标记

═════════════════════════════════════════════════
最终结果：

> **重要说明**：保守回退模式的目标是”不断链、可排查、尽量保留其他插件内容”，不是”保证任何未来版本 AstrBot 都能 100% 无重复地清理提示词”。如果平台未来彻底改写了相关注入文案，本插件会优先保证回复继续可用，并通过日志明确提示当前兼容识别失败。extra_user_content_parts 路径只有在完整识别为平台 GCC 群聊历史块时才删除；一旦不确定，就保留该块（不丢消息），可通过日志观察并更新匹配规则。

> **边界说明**：这里的兼容增强是“安全吸收长期注入内容”，不是“让第三方对 `req.prompt` / `req.contexts` 的任意改写都原样生效”。若第三方直接整体改写 prompt，或塞入与长期记忆无关的运行时中间态，本插件会宁可跳过，也不会贸然并入最终请求。

## 为什么用"短消息"调用再替换？

你可能会问：既然最终要替换成完整上下文，为什么不一开始就直接传完整内容？

这是因为 `event.request_llm()` 调用后会触发 Hook 链，其中一些插件（如 LivingMemory 记忆插件）需要**短消息**来做向量检索：

```
event.request_llm(prompt = "你们觉得去哪好？")   ← 短消息
        ↓
LivingMemory Hook（优先级 0）：
  用 "你们觉得去哪好？" 做向量搜索
  找到相关记忆，追加到 system_prompt
        ↓
本插件 Hook（优先级 -1）：
  LivingMemory 追加的记忆 → 被保留在 system_prompt 中 ✅
  替换 prompt = 完整上下文  ← 此时再换成完整的
```

如果一开始就传完整上下文（几百条历史消息），LivingMemory 会用整个历史去做向量搜索，效果很差而且浪费算力。

而当前版本比旧版多了一层兼容增强：
- 如果 LivingMemory 或其他插件在这一步之后，又把长期记忆说明前缀/后缀追加到了 `req.prompt`，插件会尝试把这些说明吸收到一个**固定、有边界标记**的兼容补充区，而不是直接把整段 prompt 生硬覆盖回去。
- 如果它们把长期记忆结果以 fake tool call / 稳定 `contexts` 结构写进 `req.contexts`，插件也会尝试把这些内容安全追加回最终上下文。
- 这样做的目标不是“让所有第三方随便改什么都生效”，而是让**长期提示词尽量被 AI 看见，同时版式清楚、边界明显、不会把脏的运行时中间态混进来**。

## 为什么仍建议开启平台的"群聊上下文感知"？

> 这是最容易让人困惑的问题：既然本插件已经接管了上下文注入，为什么仍建议在 AstrBot 平台设置里开启**聊天记忆增强（群聊上下文感知）**？

### 原因：旧平台历史与图片描述更依赖平台侧记录

本插件的上下文来源分两部分：

```
┌──────────────────────────────────────────────────────────────┐
│              插件的历史消息读取策略                            │
├──────────────────────────────────────────────────────────────┤
│                                                              │
│  优先级 1：读取平台官方存储                                  │
│  ┌────────────────────────────────────────────────┐         │
│  │ platform_message_history 表（SQLite 数据库）    │         │
│  │                                                 │         │
│  │ • 由 AstrBot 平台的 LTM 系统写入              │         │
│  │ • 数据持久化，重启后不丢失                     │         │
│  │ • 包含完整的群聊消息记录                       │         │
│  │ • 插件通过 context.message_history_manager     │         │
│  │   读取这个表中的数据                           │         │
│  └────────────────────────────────────────────────┘         │
│         ↑                                                    │
│         │  如果读取成功 → 使用这个                           │
│         │  如果读取失败 ↓                                    │
│                                                              │
│  优先级 2：回退到插件自定义存储                              │
│  ┌────────────────────────────────────────────────┐         │
│  │ custom_storage（插件自己的 JSON 文件）          │         │
│  │                                                 │         │
│  │ • 由插件自己写入和管理                         │         │
│  │ • 作为备用数据源                               │         │
│  │ • 受 custom_storage_max_messages 限制          │         │
│  └────────────────────────────────────────────────┘         │
│                                                              │
└──────────────────────────────────────────────────────────────┘
```

**关键点**：在旧版 AstrBot（≤4.25.1）中，`platform_message_history` 表主要依赖平台 LTM（聊天记忆增强）在 `on_message` 事件中写入，因此旧平台应开启"群聊上下文感知"。新版 AstrBot（≥4.25.2）中，插件也会在成功处理、缓存转正、冷群转正等路径写入官方会话与自定义存储；即使平台 GCC 没有注入上下文，主链路仍可继续运行。缓存转正写入 `platform_message_history` 会使用稳定 checkpoint 去重，避免极端并发/重试产生重复记录。但为了让历史、图片描述和其他插件读取到更完整的群聊记录，仍建议开启平台群聊上下文感知。

### 平台 LTM 的双存储机制

AstrBot 平台的 LTM 系统实际上有**两套独立的存储**：

```
┌─────────────────────────────────────────────────────────────────┐
│         AstrBot 平台 LTM 系统的两套存储                         │
├─────────────────────────────────────────────────────────────────┤
│                                                                  │
│  存储 A：内存中的 session_chats / raw_records（临时）              │
│  ┌──────────────────────────────────────────────────┐           │
│  │ dict: { "平台:群聊:群号": ["消息1", "消息2", ...] }│          │
│  │ 旧版 ≤4.25.1: session_chats（list）               │          │
│  │ 新版 ≥4.25.2: raw_records（deque）                │          │
│  │                                                    │          │
│  │ • 纯内存，重启后清空                              │          │
│  │ • 受 group_message_max_cnt 限制（默认 300）       │          │
│  │ • 格式：[发送者/HH:MM:SS]: 消息内容              │          │
│  │ • 旧版用途：on_llm_request 中注入到 system_prompt │          │
│  │ • 新版用途：on_llm_request 中注入到               │          │
│  │   extra_user_content_parts（<system_reminder>）    │          │
│  │                                                    │          │
│  │ ★ 本插件在 on_llm_request 中会删除/过滤这部分 ★  │          │
│  │   （因为插件用自己的格式化历史替代了它）          │          │
│  └──────────────────────────────────────────────────┘           │
│                                                                  │
│  存储 B：数据库中的 platform_message_history（持久）            │
│  ┌──────────────────────────────────────────────────┐           │
│  │ SQLite 表：data/data_v4.db                        │          │
│  │                                                    │          │
│  │ • 持久化存储，重启后保留                          │          │
│  │ • 无最大条数限制（平台不会自动清理）              │          │
│  │ • 包含完整消息结构（发送者、时间、内容等）        │          │
│  │ • 用途：供其他插件读取群聊历史                    │          │
│  │                                                    │          │
│  │ ★ 本插件从这里读取历史消息 ★                    │          │
│  │   （读取时受 history_cutoff.json 截止时间戳过滤， │          │
│  │    gcp_reset 后的旧消息会被自动跳过）             │          │
│  └──────────────────────────────────────────────────┘           │
│                                                                  │
│  存储 C：conversations 表（LLM 对话上下文）                     │
│  ┌──────────────────────────────────────────────────┐           │
│  │ SQLite 表：data/data_v4.db（同库不同表）          │          │
│  │                                                    │          │
│  │ • 存储 OpenAI 格式的 LLM 对话记录                 │          │
│  │ • 平台 /reset 将其清空为 []                       │          │
│  │ • ⚠️ 截止时间戳对此表不生效                       │          │
│  │   （消息无 created_at 字段，过滤无效）            │          │
│  │ • 彻底清空需同时执行 gcp_reset_here + /reset      │          │
│  └──────────────────────────────────────────────────┘           │
│                                                                  │
│  三套存储互相独立，不同步                                       │
│                                                                  │
└─────────────────────────────────────────────────────────────────┘
```

所以实际上发生的事情是：

1. 平台 LTM/GCC 收到消息 → 写入 session_chats/raw_records（内存）+ platform_message_history（数据库；旧平台尤其依赖该开关）
2. 本插件需要回复时 → 从 platform_message_history（数据库）读取历史
3. 平台在 on_llm_request 中注入群聊历史——旧版 LTM 注入到 system_prompt 或 prompt，新版 GCC 注入到 extra_user_content_parts（`<system_reminder>` 块）
4. 本插件在 on_llm_request 中**删除/过滤**平台注入的内容，**替换**成自己格式化的历史。旧版路径由 SystemPromptRewriter 剥离 system_prompt/prompt 中的 LTM 片段，新版路径由 L1/L2 双层匹配过滤 extra_user_content_parts 中的 GCC 块

**一句话总结：插件优先复用平台/官方存储和当前会话读取能力，并以自定义存储兜底；不需要平台帮它"注入"上下文。收集和保存尽量多路冗余，注入由插件统一接管。**

### AstrBot 4.25.2 变更：LongTermMemory → GroupChatContext

AstrBot 4.25.2 对群聊上下文感知模块进行了重构（#8226，优化缓存命中率），内部类名和注入通道发生变化：

| 项目 | 旧版（≤4.25.1） | 新版（≥4.25.2） |
|------|----------------|----------------|
| 类名 | `LongTermMemory` | `GroupChatContext` |
| 实例属性 | `star_inst.ltm` | `star_inst.group_chat_context` |
| 内存存储属性 | `session_chats`（`dict[str, list]`） | `raw_records`（`dict[str, deque]`） |
| 注入目标（Normal 模式） | `req.system_prompt` | `req.extra_user_content_parts` |
| 注入目标（Active Reply 模式） | `req.prompt` | `req.extra_user_content_parts` |
| 注入格式 | `"You are now in a chatroom. The chat history is as follows:\n..."` | `"<system_reminder>You are in a group chat. Belows are group chat context after your last reply:\n--- BEGIN CONTEXT---\n...\n--- END CONTEXT ---\n</system_reminder>"` |

**本插件的兼容机制**：

1. **图片描述提取**（`platform_ltm_helper.py`）：通过 `hasattr` 运行时检测 `session_chats`（旧版）或 `raw_records`（新版），两种存储结构均可正常提取图片描述，无需任何配置变更。

2. **重复历史去重**（`main.py` `on_llm_request`）：旧版 LTM 注入到 `system_prompt`/`prompt` → 插件替换这些字段时自然覆盖；新版 GCC 注入到 `extra_user_content_parts` → 只有在精确文案或结构特征同时满足 `<system_reminder>` 框架、begin/end 分隔符、平台记录行格式时才过滤移除。两层同时失效时，最坏情况只是出现重复上下文（fail-safe，不会丢消息）。

3. **实例查找**（`_get_platform_ltm`）：6 个查找分支均同时检测 `hasattr(star_inst, "ltm")`（旧版）和 `hasattr(star_inst, "group_chat_context")`（新版），无论平台版本均能找到正确的实例。

**版本兼容性**：以上机制对用户透明——相同配置在 AstrBot ≤4.25.1 和 ≥4.25.2 上均能正常工作，无需手动切换。

### group_message_max_cnt 与插件的关系

| 配置项 | 属于 | 影响 |
|--------|------|------|
| 平台 `group_message_max_cnt`（默认 300） | AstrBot 聊天记忆增强 | 只限制**内存中 session_chats / raw_records** 的条数。本插件会删掉/过滤掉这部分内容，所以**对本插件无直接影响** |
| 插件 `max_context_messages`（默认 -1） | 本插件 | 限制插件从数据库读取后**传给 AI 的最大条数**；`-1` 表示配置层不额外限制，但仍受系统保护硬上限 500 条约束 |
| 插件 `custom_storage_max_messages`（默认 500） | 本插件 | 限制插件**自定义备用存储**的最大条数 |

**所以 `group_message_max_cnt` 设置多少都无所谓？**

不完全是。虽然这个值不影响插件读取的历史条数（插件读的是数据库，不受这个限制），但它影响的是平台 LTM 的**内存占用**。设置太大会浪费内存（因为本插件用不上这些内存中的数据），设置太小也没问题。

**推荐设置：**

```
group_message_max_cnt: 10 ~ 50
```

理由：
- 这个值只影响平台自己的内存缓存（session_chats / raw_records），本插件会删掉/过滤掉它注入的内容
- 设成较小值（如 10-50）可以**节省内存**，因为本插件不依赖它
- 不要设成 0 或关闭，否则平台 LTM/GCC 可能不写入 platform_message_history 表
- 保留少量条数是为了确保 LTM/GCC 系统正常运行并持续向数据库写入消息

## 为什么建议开启"自动理解图片"？

### 平台的图片处理流程

当群聊中有人发送图片时，AstrBot 平台的 LTM/GCC 系统会把消息存入 `platform_message_history`。问题是：**图片怎么存？**

> **版本说明**：以下流程在 AstrBot ≤4.25.1（`LongTermMemory.handle_message()`）和 ≥4.25.2（`GroupChatContext.handle_message()`）上完全一致——两者都使用相同的消息格式化逻辑 `[{昵称}/{时间}]: [Image: 描述]`，都调用同一个 `get_image_caption()` 方法，区别仅在于最终写入的内存存储结构不同（旧版写入 `session_chats` 的 `list`，新版写入 `raw_records` 的 `deque`）。数据库写入（`platform_message_history` 表）不受此差异影响。

```
                  群友发了一张图片
                        ↓
          平台 LTM/GCC handle_message()
           （新旧版本格式化逻辑相同）
                        ↓
              ┌─────────┴─────────┐
              ↓                   ↓
    自动理解图片: 关闭      自动理解图片: 开启
              ↓                   ↓
    存入数据库的内容：       存入数据库的内容：
    "[Alice/14:23:45]:      "[Alice/14:23:45]:
     [Image]"                [Image: 一只橘猫
                              趴在桌子上睡觉]"
              ↓                   ↓
    插件读取到的是：         插件读取到的是：
    "[Image]"               "[Image: 一只橘猫
     ↓                       趴在桌子上睡觉]"
    AI 只知道"有图"          ↓
    但不知道图里是什么       AI 知道图片内容！
```

**关键点**：平台的"自动理解图片"功能会在 LTM/GCC 存储消息时，调用 AI 对图片进行描述，并把描述文本存入 `platform_message_history`。当本插件后续从数据库读取历史时，就能拿到带图片描述的消息。不开启时，未解析的历史图片通常只剩 `[Image]` 这类无语义占位；插件在缓存/窗口缓存路径中会移除这类未解析图片占位，只保留已解析出的图片描述和其他文本/媒体标记。

### 插件的平台图片描述提取机制（`platform_ltm_helper`）

上述流程保证了**历史消息**中的图片有描述，但插件还需要在**当前消息到达时、平台刚处理完图片描述的瞬间**，从平台的内存存储中提取描述文本，用于替换掉原始的 `[Image]` 占位符。这个提取工作由 `platform_ltm_helper.py` 完成。

**新旧版本差异与插件适配**：

| 步骤 | 旧版平台 ≤4.25.1 | 新版平台 ≥4.25.2 | 插件如何统一处理 |
|------|-----------------|-----------------|----------------|
| **1. 找到平台实例** | 遍历 6 种上下文查找路径，检测 `hasattr(star_inst, "ltm")` 找到 `LongTermMemory` 实例 | 同 6 条路径，检测 `hasattr(star_inst, "group_chat_context")` 找到 `GroupChatContext` 实例 | 每条路径**同时检测两个属性**，先 `.ltm` 再 `.group_chat_context`，无论新旧版都能命中 |
| **2. 读取会话数据** | `ltm.session_chats.get(umo, [])` → 返回 `list` | `ltm.raw_records.get(umo, [])` → 返回 `deque`，包一层 `list()` 转成统一列表 | `_get_ltm_data()` 辅助函数：先 `hasattr("session_chats")`，再 `hasattr("raw_records")`，对外统一返回 `list` |
| **3. 检查会话是否存在** | `umo in ltm.session_chats and bool(ltm.session_chats.get(umo))` | `umo in ltm.raw_records and bool(ltm.raw_records.get(umo))` | `_ltm_has_session()` 辅助函数：同样先旧后新，同时检查 key 存在性和值非空性 |
| **4. 时间戳匹配 + 前缀校验 + 图片标记识别** | 从 `session_chats[-1]` 开始倒序遍历，匹配 `[{昵称}/{时间}]:` 前缀，检测 `[Image]` 或 `[Image: 描述]` 标记 | 同左 | **上层逻辑完全不变**——步骤 2 已经把数据统一为 `list`，后续的时间戳匹配、前缀校验、`[Image]` 标记识别全部与底层存储类型解耦 |
| **5. 等待与重试** | 平台异步处理图片描述需要时间，`_should_wait_for_platform` 检查会话是否有新记录，轮询等待直到提取成功或超时 | 同左 | 等待逻辑也通过辅助函数读写，不受存储类型影响；多图场景具备进度感知——追踪 `[Image:]` 标记数量变化，有进展则重置停滞计数器，停滞或总超时时若有部分图片已完成描述则返回部分结果，不再全量丢弃 |

**为什么最终效果一致**：新旧版平台的 `handle_message()` 格式化消息的逻辑完全相同（都使用 `[{昵称}/{时间}]: [Image: 描述]` 格式），都调用同一个 `get_image_caption()` 方法。唯一的区别是内存存储容器的类型（`list` vs `deque`），而插件的辅助函数（`_get_ltm_data` / `_ltm_has_session`）将这一差异封装掉，上层提取逻辑看到的永远是统一格式的 `list` 数据。因此无论新旧版本平台，插件从平台内存中提取到的图片描述文本完全一致。

### 那本插件自己的图片处理呢？

本插件有自己的 `enable_image_processing` / `image_to_text_provider_id` 图片处理功能，但两者作用在**不同的时间点**：

```
┌──────────────────────────────────────────────────────────────┐
│            两套图片处理的作用时机对比                          │
├──────────────────────────────────────────────────────────────┤
│                                                              │
│  时机 1：消息被存入历史时（平台"自动理解图片"）             │
│  ┌────────────────────────────────────────────────┐         │
│  │ 群友发图 → 平台 LTM → 调用 AI 描述图片       │         │
│  │         → 存入 "[Image: 描述文本]" 到数据库   │         │
│  │                                                │         │
│  │ 影响：历史消息中的图片有没有描述               │         │
│  │ 没开启 → 历史中只有 "[Image]"，AI 看不懂     │         │
│  │ 开启   → 历史中有 "[Image: 描述]"，AI 能理解 │         │
│  └────────────────────────────────────────────────┘         │
│                                                              │
│  时机 2：当前消息被处理时（插件"图片处理"）                 │
│  ┌────────────────────────────────────────────────┐         │
│  │ 群友发图 → 插件概率筛选通过                   │         │
│  │         → 插件调用 AI 描述图片                │         │
│  │         → 把描述嵌入当前消息传给 AI           │         │
│  │                                                │         │
│  │ 影响：当前这一条消息中的图片有没有描述         │         │
│  │ 只在插件决定处理当前消息时才会调用             │         │
│  └────────────────────────────────────────────────┘         │
│                                                              │
│  总结：                                                      │
│  • 平台的 → 负责让 "历史消息" 中的图片有描述               │
│  • 插件的 → 负责让 "当前消息" 中的图片有描述               │
│  • 两者互补，不冲突                                         │
│                                                              │
└──────────────────────────────────────────────────────────────┘
```

### 如果只开插件的图片处理，不开平台的？

历史消息中所有图片都会变成 `[Image]`（无描述），AI 在回复时看不懂历史中的图片内容。当前消息的图片可以处理，但上下文中的历史图片信息会丢失。

### 如果只开平台的，不开插件的？

历史消息中的图片会有描述，但当前触发回复的这条消息中的图片可能没有被处理（取决于插件的 `image_to_text_scope` 配置和概率筛选结果）。

### 当前消息图片的降级语义

插件当前消息链路按原消息顺序处理每张图片：

- `enable_image_processing=false` 或当前消息不符合 `image_to_text_scope`：直接剥离原始图片，不写入图片失败占位；过滤后严格等于空字符串 `""` 的消息会被丢弃，只剩空格、换行或制表符仍按有内容保留。
- `enable_image_processing=true` 且 `image_to_text_provider_id` 留空：走多模态直传，内联 `[图片: /path/to/image.png]` 标记（路径紧跟在标记右边）并通过 `image_urls` 传递原始图片数据给多模态 AI；此路径不受 `max_images_per_message` 截断，单张图片路径提取失败时该位置降级为 `[图片（识别失败）]`。
- `image_to_text_provider_id` 已配置：先查图片描述缓存，命中则写 `[图片内容: ...]`；未命中再调用视觉模型；仍失败的图片写 `[图片（识别失败）]`，并不继续向下传递原始图片。

缓存与窗口缓存会清空不可长期依赖的 `image_urls`，并移除无语义原始占位 `[图片]` / `[Image]` 以及图片识别失败占位；`[图片内容: ...]`（AI 转换）、`[Image: xxx]`（平台自动理解）和 `[图片: /path/to/image.png]`（多模态直传内联路径，与视频/语音/文件标记一致）会保留。经过所有过滤后只有严格空字符串 `""` 会被丢弃；空格、换行、制表符等空白字符串仍视为有内容保留。

### 推荐做法

**两个都开启**，各司其职：

| 设置 | 推荐值 | 说明 |
|------|--------|------|
| 平台 `image_caption`（自动理解图片） | **开启** | 确保历史消息中的图片有描述 |
| 平台 `image_caption_provider_id` | 配置一个轻量模型 | 用于自动描述历史图片 |
| 插件 `enable_image_processing` | **开启** | 让当前消息中的图片能被转写或多模态直传；关闭时会直接剥离原始图片 |
| 插件 `image_to_text_provider_id` | 配置一个视觉模型（推荐）或留空走多模态直传 | 用于描述当前消息的图片；留空时要求回复模型支持图片 |

> 两者可以使用同一个 AI 提供商，也可以分别配置不同的模型（比如平台用便宜的，插件用精确的）。

## 推荐的平台设置

综合以上分析，使用本插件时，AstrBot 平台的"聊天记忆增强"应该这样配置。

> **版本兼容性**：以下配置在 AstrBot ≤4.25.1 和 ≥4.25.2 上均适用。4.25.2 起内部实现从 `LongTermMemory` 重构为 `GroupChatContext`，但配置项名称和含义不变。无论新旧版本，本插件均已自动适配——图片描述提取兼容两套存储结构，重复历史去重覆盖三种注入通道（`system_prompt` / `prompt` / `extra_user_content_parts`），无需针对平台版本做差异化配置。

| 平台配置项 | 推荐值 | 原因 |
|-----------|--------|------|
| 群聊上下文感知 | **开启（旧平台尤其必要，新平台也建议）** | 旧平台依赖它写入官方平台历史；新平台即使不注入也能由插件官方/自定义存储兜底，但开启后历史和图片描述更完整 |
| 最大消息数 (`group_message_max_cnt`) | `10` ~ `50` | 只影响平台内存缓存（本插件会删掉/过滤掉注入的内容），设小节省内存 |
| 自动理解图片 (`image_caption`) | **开启** | 让历史消息中的图片有文字描述 |
| 群聊图片转述模型 | 配置一个视觉模型 | 用于生成图片描述文本 |
| 主动回复 (`active_reply`) | **关闭** | 本插件有自己的主动对话系统，两者会冲突 |
| 只 @ 机器人是否触发等待 (`empty_mention_waiting`) | **关闭** | 平台的群级别空 @ 等待会劫持任意用户的下一条消息并人工插入 @bot，导致插件认错发送者。本插件的[群聊等待窗口](CONFIG_REFERENCE.md#群聊等待窗口)按用户粒度隔离，功能更精细、不会误伤。如需空 @ 等待行为，请开启插件的 `enable_group_wait_window` 代替 |
| 空 @ 触发等待后是否回复 (`empty_mention_waiting_need_reply`) | **关闭** | 依赖 `empty_mention_waiting`，上一条关闭后此项自动失效 |

## 记忆插件的兼容性：为什么要用适配过的记忆插件？

### 实际上不止两次 AI 调用，而且调用路径并不相同

前文为了便于理解，主要先讲了**普通回复流程**。但如果讨论“为什么最好使用适配过的记忆插件”，只看普通回复是不够的。

实际运行时，本插件里和“记忆能不能被 AI 看见”直接相关的，至少有下面 4 类 AI 调用：

```
┌──────────────────────────────────────────────────────────────────────────────┐
│ 1. 读空气决策 AI（要不要回复）                                              │
│    调用方式：provider.text_chat()                                           │
│    特点：直连 provider，完全绕过 Hook 链                                     │
│                                                                              │
│ 2. 普通回复生成 AI（回复什么）                                              │
│    调用方式：event.request_llm()                                             │
│    特点：会经过 Hook 链，未适配插件只有这里最容易注入记忆                     │
│                                                                              │
│ 3. 主动对话预判断 AI（现在适不适合主动开口）                                │
│    调用方式：provider.text_chat()                                           │
│    特点：同样直连 provider，完全绕过 Hook 链                                 │
│                                                                              │
│ 4. 主动对话生成 AI（主动说什么）                                            │
│    调用方式：provider.text_chat() + 运行前手动触发一次 on_llm_request Hook   │
│    特点：虽然会尝试兼容其他插件，但没有“当前用户短消息”可供未适配记忆插件检索 │
└──────────────────────────────────────────────────────────────────────────────┘
```

所以，**“未适配的记忆插件能不能生效”不能只看普通回复最终生成这一步，而要看它能不能覆盖整条链路里的不同 AI 调用方式。**

### 未适配的记忆插件：通常只有普通回复流程的最终生成 AI 能稳定看到记忆

假设你安装了一个本插件**未适配**的记忆插件（不是 LivingMemory 也不是 Legacy），它通常依赖 AstrBot 的标准 `on_llm_request` Hook 工作，常见方式是：

- 在 Hook 里向 `system_prompt` 注入记忆内容；或
- 在 Hook 里拿 `req.prompt` 当检索词，再召回记忆后注入。

这种插件在不同 AI 调用点上的表现，其实是这样的：

```
场景：使用未适配的记忆插件
════════════════════════════════════════════════════════════

  1. 读空气决策 AI（provider.text_chat）
  ┌────────────────────────────────────────┐
  │  记忆：❌ 没有                         │
  │  原因：直接调用 provider，不经过 Hook │
  └────────────────────────────────────────┘

  2. 普通回复生成 AI（event.request_llm）
  ┌────────────────────────────────────────┐
  │  记忆：✅ 有机会看到                   │
  │  原因：会经过 Hook，且这里有“当前用户 │
  │  消息短文本”可供未适配记忆插件检索    │
  └────────────────────────────────────────┘

  3. 主动对话预判断 AI（provider.text_chat）
  ┌────────────────────────────────────────┐
  │  记忆：❌ 没有                         │
  │  原因：同样直接调用 provider，不经过  │
  │  Hook                                  │
  └────────────────────────────────────────┘

  4. 主动对话生成 AI（text_chat + 手动触发 Hook）
  ┌────────────────────────────────────────┐
  │  记忆：❌ 通常也看不到                 │
  │  原因：虽然流程里会尝试触发 Hook，     │
  │  但主动对话没有“当前用户这句话”这个    │
  │  检索入口；对依赖标准 Hook / req.prompt│
  │  的未适配记忆插件来说，通常拿不到有效  │
  │  检索词，因此无法稳定注入有意义记忆    │
  └────────────────────────────────────────┘
```

也就是说，很多人容易误以为“未适配的记忆插件也能用”，其实往往只是因为**普通回复最终生成**这一步看起来像是生效了。

但从整条链路看：

- **读空气 AI** 看不到记忆
- **主动对话预判断 AI** 看不到记忆
- **主动对话生成 AI** 对未适配插件来说通常也看不到稳定、有效的记忆
- 真正比较容易看到记忆的，往往只有 **普通回复流程的最终生成 AI**

**结论：未适配的记忆插件通常只能影响“普通回复最后说什么”，却无法稳定影响“要不要回复”“要不要主动开口”以及“主动对话说什么”这些更前面的关键判断和生成环节。**

### 适配过的记忆插件：关键流程都能按插件自己的方式拿到记忆

当使用本插件适配的记忆插件（LivingMemory 或 Legacy），并开启 `enable_memory_injection` 时，情况就不一样了：

- 本插件不会被动等待外部 Hook“碰巧注入成功”
- 而是会**主动调用记忆插件接口取回记忆文本**
- 然后把记忆嵌入到自己掌控的上下文里

因此，只要是本插件自己构建上下文的关键 AI 流程，适配插件都能跟着生效。

```
场景：使用适配过的记忆插件 + enable_memory_injection = true
════════════════════════════════════════════════════════════

  普通回复流程
  ┌─────────────────── memory_insertion_timing 配置 ───────────────────┐
  │                                                                     │
  │  "pre_decision"（决策前注入）        "post_decision"（决策后注入） │
  │                                                                     │
  │  读空气决策 AI        ✅ 有记忆      读空气决策 AI        ❌ 无记忆 │
  │  普通回复生成 AI      ✅ 有记忆      普通回复生成 AI      ✅ 有记忆 │
  │                                                                     │
  └─────────────────────────────────────────────────────────────────────┘

  主动对话流程
  ┌─────────────────────────────────────────────────────────────────────┐
  │  主动对话链路里，记忆会先被嵌入 final_message，随后再进入：         │
  │                                                                     │
  │  1. 主动对话预判断 AI   ✅ 有记忆                                   │
  │  2. 主动对话生成 AI     ✅ 有记忆                                   │
  │                                                                     │
  │  也就是说，主动对话这条链路里，预判断和最终生成都会看到同一份记忆。 │
  └─────────────────────────────────────────────────────────────────────┘
```

其中需要特别注意：

- `memory_insertion_timing` 主要影响的是**普通回复流程里的读空气决策 AI**是否能提前看到记忆
- **主动对话流程**里，记忆注入发生在预判断和生成之前，因此这两步都能看到记忆

### 完整对比

| 场景 | 读空气决策 AI | 普通回复生成 AI | 主动对话预判断 AI | 主动对话生成 AI | 说明 |
|------|:---:|:---:|:---:|:---:|------|
| 未适配的记忆插件 | ❌ | ✅ | ❌ | ❌ | 外部插件依赖标准 Hook；真正稳定生效的通常只有普通回复最终生成 |
| 适配插件 + `post_decision` | ❌ | ✅ | ✅ | ✅ | 普通回复在决策后注入；主动对话链路仍会在预判断/生成前拿到记忆 |
| 适配插件 + `pre_decision` | ✅ | ✅ | ✅ | ✅ | 普通回复与主动对话两条链路都能在关键步骤看到记忆 |

### 判断型AI为什么单独支持人格开关/指定人格？

本插件现在只给三类“判断型AI”提供独立的人格控制：

- 读空气AI
- 主动对话预判断AI
- 频率判断AI

原因不是它们更重要，而是它们的职责不同：

- 这三者的本质任务都是**做判断**
- 回复生成AI / 主动对话生成AI 的本质任务是**直接按当前会话人格输出内容**

当某个人格提示词写得很强、很像“必须沉浸扮演”的角色卡时：
- 对生成型AI来说，这通常是合理的
- 但对判断型AI来说，模型可能会把自己理解成“我现在要进入角色去表演”，而不是“我要先冷静判断该不该回 / 该不该主动开口 / 现在是不是话太多”

因此，判断型AI现在支持：
- 保持默认：跟随当前会话当前生效人格
- 单独关闭人格注入：改为中性判断任务
- 单独指定一个更适合做判断的人格

这是一种**最小侵入**方案：只动最容易被人格干扰的判断层，不改变最终回复生成层原本应有的会话人格行为。

### 回复生成AI为什么仍然跟随当前会话人格？

因为回复生成AI和主动对话生成AI的职责，本来就是直接产出要发出去的话：

- 它们需要真正“像这个人格一样说话”
- 它们不该脱离当前会话人格单独运行
- 它们仍然会在每次调用时重新获取当前会话当前生效的人格，因此切换人格后可以立即生效

### 判断型AI的人格选择规则

三类判断型AI统一遵循以下规则：

1. **默认**：自动包含人格，且默认取当前会话当前生效的人格
2. **若关闭包含人格**：按中性判断任务执行，不额外注入人格
3. **若填写指定人格名**：只对该判断型AI固定使用该人格
4. **若指定人格名无效**：自动回退到当前会话人格，不中断主流程

⚠️ 指定人格名必须填写**完整名称**，不会做模糊匹配。
### 为什么决策 AI 有没有记忆很重要？

决策 AI 的任务是判断"现在要不要回复这条消息"。在本插件的决策提示词中，明确写了：

> **有记忆时更倾向于回复**，特别是：
> - 消息与记忆内容高度相关
> - 记忆显示与当前发送者有重要互动历史

也就是说，如果决策 AI 有记忆，它能做出更"人性化"的判断：

```
没有记忆的决策 AI：
  "张三说了'还记得上次那件事吗？'" → 不知道什么事 → 可能判断为不回复

有记忆的决策 AI：
  "张三说了'还记得上次那件事吗？'"
  + 记忆显示：上次和张三讨论了一个有趣的话题
  → 这个人跟我聊过！这条消息很相关！→ 判断为应该回复
```

### 为什么外部记忆插件不能注入到决策 AI？

根本原因是**调用方式不同**：

```
决策 AI：
  provider.text_chat(prompt, contexts, system_prompt)
  │
  │  这是直接调用 AI 提供商的底层 API
  │  完全不触发平台的 Hook 机制
  │  外部插件无法感知这次调用的存在
  │
  └→ 所以外部记忆插件的 on_llm_request Hook 根本不会被触发

回复 AI：
  event.request_llm(prompt, contexts, system_prompt)
  │
  │  这是通过平台标准流程调用
  │  会触发完整的 Hook 链
  │  外部插件可以在 Hook 中修改请求
  │
  └→ 外部记忆插件的 Hook 会被触发，可以注入到 system_prompt
```

**这不是设计缺陷，而是有意为之**——决策 AI 需要轻量快速地做判断，如果走 Hook 链，其他插件的修改可能干扰决策逻辑。但这也意味着，只有本插件**主动适配**的记忆插件才能把记忆送到决策 AI 面前。

### 推荐做法

| 推荐等级 | 做法 | 效果 |
|:---:|------|------|
| ⭐⭐⭐ | 使用适配的记忆插件 + `pre_decision` | 决策和回复都有记忆，AI 表现最好 |
| ⭐⭐ | 使用适配的记忆插件 + `post_decision` | 回复有记忆，决策无记忆 |
| ⭐ | 使用未适配的记忆插件 | 只有回复有记忆，决策完全无记忆 |

**目前适配的记忆插件：**

| 插件 | 配置模式 | 说明 |
|------|----------|------|
| [strbot_plugin_play_sy](https://github.com/kjqwer/strbot_plugin_play_sy) | `memory_plugin_mode: "legacy"` | 传统模式，稳定性高 |
| [astrbot_plugin_livingmemory](https://github.com/lxfight-s-Astrbot-Plugins/astrbot_plugin_livingmemory) | `memory_plugin_mode: "livingmemory"` | 智能模式，混合检索+人格隔离 |
| 自动检测（推荐） | `memory_plugin_mode: "auto"` | 自动检测已安装的记忆插件，无需手动选择 |

### auto 模式详解

`memory_plugin_mode: "auto"`（默认值）会在每次需要记忆注入时**自动检测**当前已安装且可用的记忆插件，按以下优先级选择：

```
检测优先级：LivingMemory v2 → LivingMemory v1 → Legacy
```

| 安装情况 | auto 模式行为 |
|----------|---------------|
| 只安装了 LivingMemory | 自动使用 LivingMemory（自动检测 v2/v1 版本） |
| 只安装了 Legacy | 自动使用 Legacy |
| 两个都安装了 | **优先使用 LivingMemory**（功能更强大），忽略 Legacy |
| 两个都没安装 | **自动跳过记忆注入**，不会报错，不影响其他功能正常运行 |

> **为什么推荐 auto 模式？**
> - 新用户无需了解两种记忆插件的区别，安装任意一个即可自动适配
> - 切换记忆插件时无需修改配置，卸载旧的、安装新的即可
> - 未安装记忆插件时不会产生错误日志，等安装后自动生效

### LivingMemory 双层兼容说明

当 `memory_plugin_mode = "livingmemory"` 或 auto 检测到 LivingMemory 时，当前版本会同时处理两层兼容：

1. **插件架构兼容**：`livingmemory_version`
   - `auto`（推荐）：自动识别当前插件是 `v2 initializer` 架构还是 `v1` 直挂架构
   - `v2`：强制按新架构读取 `initializer.memory_engine`
   - `v1`：强制按旧架构读取 `memory_engine`
2. **人格接口兼容**：`livingmemory_persona_compat_mode`
   - `auto`（推荐）：依次尝试 `resolve_selected_persona` → `get_default_persona_v3` → `get_personas_by_key`
   - `resolver_only` / `legacy_only` / `off`：用于排查特殊环境

> Web 面板技术树的「记忆注入」节点也已经同步展示这两个配置项，可直接在可视化界面中切换并保存。

## 其他常见问题

### 开启工具提醒后，某些 Skill / 工具出现参数串扰怎么办？

如果你发现这类现象：

- 某个 Skill / MCP 工具在**关闭本插件**时正常，**开启本插件**后更容易报错；
- 报错内容类似：
  - `unexpected keyword argument 'silent'`
  - `Tool handler parameter mismatch`
  - 某个工具收到了明显属于**另一个工具**的参数；
- 常见于需要在同一轮里混合调用 shell / python / send_message 等多种工具的 Skill；

通常说明问题更像是**工具参数提示过细导致的参数串扰**，而不是工具本身已经损坏。

#### 已内置的兼容处理

本插件现在会根据 AstrBot 当前会话的 `provider_settings.tool_schema_mode` 自动调整工具提醒细节：

- `skills_like`：只展示**工具名称 + 功能描述**，不再提前展开参数列表；
- `full`：继续展示**名称 + 描述 + 参数**；
- 旧版 AstrBot 未提供该配置时：按 `full` 兼容处理。

这样做是为了尽量不干扰 AstrBot 在 `skills_like` 下原本的两阶段工具 schema 暴露与 re-query 流程。

#### 建议排查顺序

1. **先确认 AstrBot 当前会话的 `tool_schema_mode`**
   - 如果是 `skills_like`，现在工具提醒应当只显示名称/描述；
   - 如果你仍然看到了参数列表，说明当前会话没有正确走到新的提醒降级逻辑。

2. **对照报错工具的真实签名检查是否发生了“跨工具参数混用”**
   - 例如 `astrbot_execute_shell` 只接受 `command / background / env`；
   - 若日志里却出现了 `silent` 之类本应属于 Python 工具的参数，就属于典型串扰。

3. **确认问题是否只出现在少数 Skill / MCP 工具上**
   - 如果主要集中在“同一轮混合调用多种工具”的 Skill，基本符合参数串扰特征；
   - 如果所有工具都普遍失败，则更应检查平台侧工具注册或上游模型状态。

4. **临时验证手段**
   - 保持插件开启，先关闭 `enable_tools_reminder` 再复测；
   - 若问题明显缓解，通常可以确认是提醒层提示干扰，而不是实际工具集损坏。

#### 什么时候应继续排查平台而不是插件

如果报错表现为：

- `send_message_to_user` 发送超时；
- MCP 服务器连接失败；
- `Tool not found` / `Server unavailable`；
- 工具返回内容本身为空或上游接口报错；

那更可能是 AstrBot / MCP / 协议端 / 上游服务问题，而不是本插件的工具提醒文本导致。


### Q: 我用了其他"智能回复"插件，为什么 AI 行为异常？

A: 当前版本会追踪并合并其他插件对 `system_prompt`、`prompt`、`contexts`、`extra_user_content_parts`、`image_urls`、`audio_urls` 的安全增量。长期提示词、记忆型上下文、额外补充信息和多模态附件通常都能继续被 AI 看见；只有整段重写 prompt、临时运行态或无法判定为安全增量的内容会被保守跳过。若识别失败，优先退化为”保留/可能重复”，不会为了去重误删第三方内容。

工具由 `reply_handler` 通过 `event.request_llm(tool_set=...)` 传递全平台工具集，`on_llm_request` 钩子只读不写 `req.func_tool`，由其他插件（如 maid_agent）自由管控。本插件仅基于最终工具集生成文本提醒，不拦截 AI 实际调用工具。

### Q: 为什么 AstrBot 的 `/reset` 清除历史后，AI 还记得之前的对话？

A: 插件同时使用官方会话存储和自定义备用存储，并且还维护运行时缓存、主动对话状态、注意力/概率状态等。平台 `/reset` 不一定覆盖这些插件侧状态。请使用插件的 `gcp_reset` 或 `gcp_reset_here` 指令，它会按当前会话边界清理插件维护的相关数据。

### Q: 其他修改 `system_prompt` 的插件能和本插件一起用吗？

A: 可以。只要它是在 `system_prompt` 前面插入或后面追加内容（对应兼容条件①②），本插件的 SystemPromptRewriter 会自动识别并保留。即使识别失败也会进入保守回退模式，优先保留当前内容。

### Q: 开启 `enable_debug_log` 后日志中看到的上下文是什么？

A: 是插件最终发送给 AI 的完整内容，包括格式化的历史消息、系统指令、当前消息等。这是排查问题的最佳方式。

### Q: 不开启平台的"群聊上下文感知"会怎样？

A: 旧版平台上，`platform_message_history` 和平台自动理解图片更依赖该开关，关闭后历史与图片描述可能明显不完整。新版平台上，插件自己的官方会话保存和自定义存储仍可兜底运行，但平台历史、图片说明和其他插件可读到的群聊记录会更完整。结论是：旧平台尤其需要开启，新平台也建议开启。

### Q: `group_message_max_cnt` 设成 300 会不会浪费？

A: 会略微浪费内存，但不会影响功能。旧平台会把内存群聊上下文注入到 `system_prompt`/`prompt`，新平台会注入到 `extra_user_content_parts`；本插件只在高置信度识别为平台重复群聊历史时过滤掉它们，并替换成自己的格式化历史。设成 10-50 更节省资源。

### Q: 平台的"自动理解图片"和插件的"图片处理"会重复调用 API 吗？

A: 对于**历史消息**中的图片，只有平台会调用一次（存储时）。对于**当前正在处理的消息**中的图片，如果插件决定处理，会再调用一次。两者作用在不同时机，不会对同一张图片重复调用。

## AI 回复频率相关问题

### Q: AI 回复频率太高，一直在刷屏怎么办？

A: 回复频率过高通常是概率和限制相关配置偏高导致的。按优先级依次排查和调整：

| 排查项 | 配置项 | 建议操作 |
|--------|--------|----------|
| 1. 基础概率过高 | `initial_probability` | 降低到 `0.05` ~ `0.08`（默认 `0.08`），这是没有注意力加成时的基础触发概率 |
| 2. 连续对话概率过高 | `after_reply_probability` | 降低到 `0.5` ~ `0.7`（默认 `0.8`），这是关闭注意力机制时传统模式的回复后临时提升概率 |
| 3. 回复密度限制未开启 | `enable_reply_density_limit` | 确保为 `true`，限制短时间内的最大回复次数 |
| 4. 密度窗口/上限 | `reply_density_window_seconds` / `reply_density_max_replies` | 默认 300 秒内最多 4 次，可改为 `300` 秒 / `2~3` 次 |
| 5. 对话疲劳未开启 | `enable_conversation_fatigue` | 确保为 `true`，连续对话后自动降低回复意愿 |
| 6. 时段概率未配置 | `enable_dynamic_reply_probability` | 开启后配置 `reply_time_periods`，深夜/午休时段自动降低频率 |
| 7. 平台主动回复未关闭 | AstrBot 聊天记忆增强 → 主动回复 | **必须关闭**，否则平台和插件会同时回复，频率翻倍 |
| 8. 平台空 @ 等待未关闭 | 平台设置 → 只 @ 机器人是否触发等待 | **必须关闭**，否则平台的群级别空 @ 等待会劫持任意用户的下一条消息并人工插入 @bot，导致插件认错发送者。请使用插件的[群聊等待窗口](CONFIG_REFERENCE.md#群聊等待窗口)代替 |

**快速降频方案**：将 `initial_probability` 改为 `0.03`，`after_reply_probability` 改为 `0.5`，`reply_density_max_replies` 改为 `2`。

### Q: AI 回复频率太低，基本不说话怎么办？

A: 回复频率过低的排查方向：

| 排查项 | 配置项 | 建议操作 |
|--------|--------|----------|
| 1. 基础概率太低 | `initial_probability` | 提高到 `0.10` ~ `0.15` |
| 2. 是否处于深夜/午休低频时段 | `reply_time_periods` | 检查当前时间是否命中低频时段（`factor < 1.0`），可调大对应 `factor` |
| 3. 对话疲劳阈值过低 | `fatigue_threshold_light` | 提高轻度疲劳阈值，如改为 `5`，让 AI 能连续多聊几轮 |
| 4. 频率调整器持续降频 | `enable_frequency_adjuster` | 暂时关闭观察，或调高 `frequency_min_probability`（如 `0.05`） |
| 5. 决策 AI 总是回答 NO | `decision_ai_provider_id` | 确认决策模型正常工作，开启 `enable_debug_log` 查看决策结果 |
| 6. 群组未启用 | `enabled_groups` | 留空 = 全部启用；如果填了群号，确认目标群在列表中 |
| 7. 注意力机制降低了概率 | `attention_decreased_probability` | 当 AI 对某用户注意力很低时会使用此值，可适当提高；如果你在使用传统模式，请确认 `enable_attention_mechanism` 已关闭，此项不会生效 |

**快速提频方案**：将 `initial_probability` 改为 `0.15`，`after_reply_probability` 改为 `0.85`，暂时关闭 `enable_conversation_fatigue`。

### Q: AI 回复频率忽高忽低、不稳定？

A: 这通常是多个动态系统叠加的正常表现。如果波动过大，可以逐一排查：

1. **频率调整器**（`enable_frequency_adjuster`）：每隔一段时间自动分析群聊节奏并调整概率，可能导致突然升降。如果不需要可以关闭
2. **注意力机制**（`enable_attention_mechanism`）：对不同用户有不同注意力值，会影响触发概率；关闭后会完全回退到传统回复后提升模式，不会再触发注意力溢出、注意力冷却等注意力专属机制
3. **动态时段概率**（`enable_dynamic_reply_probability`）：在时段切换的过渡期（`reply_time_transition_minutes`）概率会平滑变化
4. **对话疲劳**（`enable_conversation_fatigue`）：连续对话后突然降频是疲劳系统生效，等 `fatigue_reset_threshold` 秒后会恢复

**建议**：开启 `enable_debug_log`，观察日志中各系统对概率的实际影响值。

## AI 读空气判断相关问题

### Q: AI 读空气总是判断为不回复（NO），该怎么调？

A: "读空气"由决策 AI 负责，它会综合上下文判断当前是否应该回复。如果总是 NO：

1. **检查决策 AI 模型**：`decision_ai_provider_id` 所配置的模型是否正常工作？某些轻量模型可能理解力不足，总是保守回答 NO
2. **调整决策提示词**：通过 `decision_ai_extra_prompt` 追加提示，例如：`"你应该更积极地参与对话，当有人在讨论有趣的话题时倾向于回复 YES"`
3. **检查提示词模式**：`decision_ai_prompt_mode` 设为 `"append"` 是追加模式，`"override"` 会完全替换内置提示词（不推荐，除非你很清楚在做什么）
4. **注意力和记忆**：如果用了适配的记忆插件且 `memory_insertion_timing` 设为 `"pre_decision"`，记忆会帮助决策 AI 做出更准确的判断。没有记忆时决策 AI 可能偏保守
5. **概率筛选先行**：读空气判断是第二层筛选，消息必须**先通过概率筛选**才会进入读空气判断。确保 `initial_probability` 不会太低导致大部分消息在概率筛选阶段就被过滤了

### Q: AI 读空气判断太宽松，什么消息都回复？

A: 如果 AI 几乎对所有消息都判断 YES：

1. **检查是否跳过了决策 AI**：@消息、触发关键词等会跳过概率和读空气判断直接回复，确认是否大量消息通过这些旁路触发
2. **调整决策提示词**：通过 `decision_ai_extra_prompt` 追加限制，例如：`"只有当消息明确与你相关、直接提问、或话题非常有趣时才回复 YES，闲聊和水群不需要回复"`
3. **更换决策模型**：某些模型可能倾向于积极回应，尝试换一个更"理性"的模型
4. **利用消息质量预判**：开启 `enable_message_quality_scoring`，纯水聊消息会被降权，减少到达决策 AI 的低质量消息

### Q: 怎么查看 AI 读空气的具体判断过程？

A: 开启 `enable_debug_log`，日志中会显示：
- 概率筛选的计算过程和结果
- 决策 AI 收到的上下文内容
- 决策 AI 的回答（YES / NO）及原因
- 各个系统（注意力、疲劳、时段等）对概率的调整详情

## Web 管理面板相关问题

### Q: Web 管理面板的默认端口是什么？怎么访问？

A: Web 管理面板的相关信息：

| 项目 | 说明 |
|------|------|
| **默认端口** | `1451` |
| **默认监听地址** | `0.0.0.0`（所有 IPv4 接口，自动启用双栈同时监听 IPv6） |
| **默认状态** | 关闭（需在插件配置中将 `enable_web_panel` 设为 `true`） |

启动成功后，AstrBot 日志中会输出完整的访问地址列表，分为三级：

| 分级 | 标签 | 示例 | 说明 |
|------|------|------|------|
| **本地** | `➜  本地` | `http://localhost:1451` / `http://127.0.0.1:1451` | 本机回环地址，仅本机可访问 |
| **内网 (IPv4)** | `➜  内网` | `http://192.168.1.2:1451` | 设备所在局域网 IPv4 地址，局域网内其他设备可访问 |
| **内网 (IPv6)** | `➜  内网` | `http://[2001:db8::1]:1451` | 设备所在局域网 IPv6 地址（链路本地地址 fe80:: 除外） |
| **公网** | `➜  公网` | `http://135.0.0.2:1451` | 通过多个公共服务自动检测并去重后的公网 IP，仅当设备存在公网 IP 且能连通外部网络时显示 |

**首次使用步骤**：

1. 在 AstrBot 插件配置中将 `enable_web_panel` 设为 `true`
2. 重启 AstrBot（或重载插件）
3. 查看 AstrBot 日志，首次启动会以 **WARNING 级别**输出**随机生成的默认密码及安全警告**
4. 根据 AstrBot 日志中输出的启动信息选择对应地址（本机用 `本地`，局域网用 `内网`，外网用 `公网`），浏览器访问并登录
5. **登录后请立即修改为自定义密码**（修改后日志中将不再输出任何密码信息，明文副本自动删除）

### Q: Web 面板打不开 / 无法访问怎么办？

A: 按以下步骤逐一排查：

**第一步：确认插件已启用 Web 面板**
- 检查 `enable_web_panel` 是否为 `true`
- 检查 AstrBot 日志中是否有 Web 面板启动成功的信息

**第二步：确认端口和地址**
- 确认 `web_panel_port`（默认 `1451`）没有被其他程序占用
- 如果修改过端口，确认访问的是正确端口

**第三步：检查防火墙**
- **Windows**：检查 Windows Defender 防火墙是否放行了对应端口
  ```
  # 以管理员身份运行 PowerShell，添加入站规则
  New-NetFirewallRule -DisplayName "GCP Web Panel" -Direction Inbound -Port 1451 -Protocol TCP -Action Allow
  ```
- **Linux**：检查 iptables / firewalld / ufw 是否放行
  ```bash
  # ufw
  sudo ufw allow 1451/tcp

  # firewalld
  sudo firewall-cmd --permanent --add-port=1451/tcp && sudo firewall-cmd --reload
  ```
- **云服务器**（阿里云/腾讯云/华为云等）：除了系统防火墙，还需在**云控制台的安全组**中放行对应端口

**第四步：Docker 部署额外检查**
- 确认容器启动时映射了端口：`-p 1451:1451`
- 如果使用 docker-compose，检查 `ports` 配置：
  ```yaml
  ports:
    - "1451:1451"
  ```
- 如果修改了 `web_panel_port`，映射也要对应修改：`-p 你的端口:你的端口`
- 确认容器内部监听地址为 `0.0.0.0`（默认值），而不是 `127.0.0.1`（`127.0.0.1` 在容器内只允许容器内部访问）

**第五步：反向代理检查**（如果使用 Nginx 等反代）
- 确认反代配置正确转发到 `127.0.0.1:1451`
- 如果反代与 Web 面板在**同一台机器**，即使未开启 `web_panel_trust_proxy`，系统也会因为检测到连接来源为回环地址（`127.0.0.1 / ::1`）而自动读取合法的 `X-Real-IP / X-Forwarded-For` 获取真实 IP
- 如果反代**不在本机**，且后端看到的连接来源不是回环地址，则需要显式开启 `web_panel_trust_proxy` 才会信任代理头
- `web_panel_trust_proxy` 现已归类为**安全边界配置**：只能在 AstrBot 传统配置界面修改，Web 面板中仅只读展示

### Q: 忘记了 Web 面板密码怎么办？

A: 两种方式重置密码：

1. **通过配置重置**：在 AstrBot 插件配置中将 `web_panel_reset_password` 设为 `true`，然后重启。密码会被重置为新的随机值并以 WARNING 级别输出到日志中（含安全警告）。重置完成后此开关会自动关闭；新密码会直接按 `Argon2id` 哈希保存
2. **删除认证文件**：删除插件数据目录下的 `web_data/auth.json` 和 `web_data/jwt_secret.json` 文件，重启后会重新生成随机密码并输出到日志

### Q: Web 面板提示"IP 已被封禁"怎么办？

被封 IP（支持 IPv4 和 IPv6）访问面板时，中间件会通过一次性错误页跳转令牌进入 `/error?code=blocked`，系统跳转能够停留在错误页；用户手动访问或刷新错误页时，会按当前 IP 状态重新分流。错误页每 5 秒自动轮询检测解封状态，封禁到期后自动跳转至登录页（已认证用户直达面板）。手动封禁可通过 Web 面板「IP 封禁管理」解封。

> 安全设计：错误页对被封禁 IP 仅展示通用"访问被拒绝"提示，不透露具体封禁原因、时长或触发机制（如防爬虫/暴力破解/黑名单），防止被封禁者研究封禁规则。`robots.txt` 对所有来源可读并声明 `Disallow: /`；错误页响应带 `X-Robots-Tag: noindex, nofollow, noarchive`，避免拦截页被正常爬虫索引。

A: 多次输入错误密码会触发暴力破解防护（分级锁定，对 IPv4 和 IPv6 均生效）：

| 失败次数 | 锁定时长 |
|:--------:|:--------:|
| 5 次 | 30 秒 |
| 10 次 | 60 秒 |
| 15 次 | 5 分钟 |
| 20 次 | 10 分钟 |
| 30 次 | 30 分钟 |
| 50 次 | 1 小时 |
| >50 次（解锁后重试） | 封禁（默认永久，可配置） |

此外系统还会监控登录频率：若某 IP 在配置的窗口期内（默认 10 秒）失败达到阈值（默认 3 次），直接封禁 IP 跳过阶梯锁定。`web_panel_brute_force_window`（默认 3600 秒）控制在多长时间无活动后自动清零失败计数，避免偶尔输错密码的用户长期累积。以上所有参数均可通过配置项调整，详见 [配置项参考](CONFIG_REFERENCE.md#暴力破解防护)。

等待锁定时间过后即可重新尝试。如果确实忘记密码，请参考上面的密码重置方法。

### Q: `web_panel_brute_force_window` 设为 0 有什么风险？

A: 此配置项控制"失败计数重置窗口"。设为零意味着失败计数**永不自动清零**（除非重启插件或登录成功）。

**极端场景**：假设你某天手误输错密码 4 次（未触发锁定），之后 3 个月没再输错。某天你又输错 1 次 → 直接触发第 5 次锁定（30 秒）。再过几个月继续累积 → 触发更长锁定，最终可能触发永久封禁。

**为什么不修？** 这是有意设计：如果系统在关闭衰减时仍自动清理，慢速暴力破解攻击者可以故意拉长尝试间隔绕过阶梯锁定。对于需要最高安全级别的公网部署，`window=0` 保证攻击者每次尝试都被永久记录。

**建议**：
- 内网/本地部署：保持默认 `3600`（1 小时），平衡安全与易用
- 公网暴露但不想误伤：设为 `86400`（24 小时）或更大值
- 需要最高安全且接受误伤风险：设为 `0`，搭配 `web_panel_protected_ips` 保护管理员 IP

### Q: 如何下载当前配置文件？

A: 在「配置流程图」或「核心设置」页面右下角有一个半透明浮窗，显示当前配置文件名。浮窗右侧有一个 **下载箭头图标（↓）**，鼠标悬停时会提示「点击下载配置文件」，点击即可将当前插件配置文件下载到本地。

**安全说明**：
- 下载功能**只读**，不会修改、删除或覆盖服务器上的任何文件
- 前端**不会暴露服务器绝对路径**，下载请求由服务端内部确定文件位置，响应中仅包含文件名和文件内容
- 必须在**登录面板后**才能使用（通过完整 JWT + 会话验证 + IP 过滤 + 防爬虫 + 已登录速率限制链路）
- 未登录、令牌失效或会话过期的请求在中间件层即被拦截（返回 401，受保护 API 不返回具体失效原因），不会执行文件读取，不消耗服务器 I/O 资源
- 下载功能受 Web 面板所有安全机制统一管控：IP 黑白名单、封禁列表、暴力破解锁定、防爬虫自动封禁、已登录请求速率限制
- 下载的文件即为插件当前生效的配置文件（`astrbot_plugin_group_chat_plus_config.json`）
- 每次下载操作均会写入 **Web 面板访问日志**（在「访问日志」页面可直接查看），附注中会标明下载成功或失败原因

### Q: 下载的配置文件可以直接修改后上传覆盖吗？

A：**不可以。** 下载功能是**纯粹的只读操作**，只提供文件内容的单向输出。它不提供上传、覆盖、删除或任何写入能力。如果需要在 Web 端修改配置，请使用「配置流程图」页面的可视化配置编辑器或「核心设置」页面的配置项，修改后点击「保存并重启插件」即可。

### Q: 点击下载按钮后提示"下载失败"怎么办？

A: 按以下步骤逐一排查。**建议同时查看 Web 面板「访问日志」页面中对应请求的状态码和附注**，可快速定位问题。

**第一步：确认浮窗可见且按钮可用**
- 下载按钮仅当右下角配置文件浮窗**正常显示**时才能点击
- 如果配置面板（右侧滑出）已打开，浮窗会临时隐藏，此时按钮不可用；关闭配置面板后浮窗会自动恢复
- 切换至其他视图（如数据可视化、会话管理等）后浮窗也会隐藏，只有「配置流程图」和「核心设置」页面会显示
- **提示**：「配置流程图」页面右下角配置文件浮窗上方还有一组**缩放控件**（+ 放大 / ⊡ 适应屏幕 / − 缩小），可用来调整流程图的显示比例，方便查看超长的配置连线。缩放控件同样会在配置面板打开或切换视图时自动隐藏

**第二步：根据错误弹窗中的 HTTP 状态码定位问题**
- **401** — 登录会话缺失、已过期或失效，刷新页面重新登录即可；具体失效原因只写入服务端日志，不通过受保护 API 响应体暴露
- **403** — 服务端拒绝了下载请求：可能是配置文件格式校验不通过、文件权限不足，或当前 IP 被封禁/未在白名单中。查看 AstrBot 日志和访问日志附注获取详细原因
- **404** — 配置文件尚未生成，请确认插件已完全启动并完成首次配置加载
- **500** — 服务端内部错误（读取异常、编码错误等），请查看 AstrBot 日志排查具体异常
- **网络错误（无状态码）** — fetch 请求本身失败，通常为网络连接问题

**第三步：检查配置文件是否存在**
- 下载功能读取的是插件真实配置文件。如果插件尚未完成首次初始化（刚安装、还未启动完全），配置文件可能尚未生成
- 等待插件完全启动后再试；如果问题持续，检查 AstrBot 日志中是否有配置文件相关的错误信息

**第四步：反向代理检查**（如果使用 Nginx/Caddy 等反代）
- 下载端点路径为 `/api/config/download`，确保反向代理**未拦截或阻断**此路径
- 该路径属于 Web 面板 API 的一部分，反代配置应将 `/api/` 路径完整转发到后端
- Nginx 示例（确认没有遗漏 `/api/` 路径的转发规则）：
  ```nginx
  location / {
      proxy_pass http://127.0.0.1:1451;
      proxy_set_header Host $host;
      proxy_set_header X-Real-IP $remote_addr;
      proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
  }
  ```
  上述配置已覆盖所有路径（包括 `/api/config/download`），无需额外规则
- 如果反代配置中单独限制了 `/api/` 路径（如只放行了特定子路径），需要补充 `/api/config/download` 的放行规则
- 如果反代有 WAF 或访问控制规则，确认下载请求不会被误判为恶意行为而拦截

**第五步：网络与防火墙检查**
- 下载是由浏览器直接发起的 `fetch` 请求，与页面访问使用同一连接。如果能正常打开面板页面，网络层面通常没有问题
- 如果浏览器控制台显示网络错误（如 `NetworkError`），检查是否存在浏览器插件拦截了下载请求
- 若使用 Docker 部署，确认容器端口映射正确（`-p 1451:1451`）

**第六步：权限问题**
- 极少数情况下，服务端可能因文件系统权限问题无法读取配置文件
- 此时 AstrBot 日志中会输出 `下载配置文件失败：权限不足` 及具体路径，访问日志附注中也会记录
- 检查插件进程是否对配置文件有读取权限（通常只要插件能正常启动，就一定有读取权限）
